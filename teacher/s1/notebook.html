Learning goals

By the end of Session 1 a student can:

  1. Install Rust with rustup and create, check, run and release-build a cargo project.
  2. Declare immutable and mutable variables, constants, and shadowed variables, and explain the difference.
  3. Pick the right scalar type for a value and handle overflow on purpose.
  4. Write functions with typed parameters and return values, using expression-based returns.
  5. Use if, loop, while and for, including if and loop as expressions.
  6. Run cargo fmt and cargo clippy and act on what they say.

Before class

  • Send the install line from the course home page a day early. Ask students to run cargo --version and bring the output.
  • Install an editor with rust-analyzer (VS Code, Zed, RustRover or Neovim). Inlay type hints are the best teaching aid you'll have this week.
  • Have the lab folder labs/lab1-robbie-greeting open, and run cargo test in it once so the build cache is warm.
  • Windows machines need the MSVC build tools; rustup-init offers to install them. Allow 10 extra minutes.

Deeper notes by topic

Why the compiler is strict

Rust's safety rules are enforced statically: the compiler proves certain bugs are impossible before the program runs. The guarantees that matter most in week 1: no null pointers in safe code (Session 3 introduces Option instead), no reading uninitialised variables, bounds-checked indexing, and no undefined behaviour from integer overflow. Next session's ownership system adds memory safety without a garbage collector.

Say it this way

"A C compiler asks: is this valid syntax? The Rust compiler asks: could this program ever do something you didn't mean? It's stricter because it's answering a harder question."

cargo and editions

cargo new writes edition = "2024". Editions are opt-in language revisions every three years (2015, 2018, 2021, 2024); crates on different editions still link together. cargo check runs the front end and the borrow checker but skips code generation, which is why it's so much faster than cargo build. target/ holds build output and should never be committed (cargo's generated .gitignore already excludes it).

Mutability, constants and shadowing

  • let bindings are immutable by default. This isn't only style: the borrow checker (Session 2) leans on it, and it helps the optimiser.
  • const is inlined wherever it's used and must be computable at compile time. static (not covered yet) is a single memory location with a fixed address.
  • Shadowing creates a new binding. The old value still exists until the end of its scope, but its name is hidden. It's idiomatic for transformations of the same concept: let input = input.trim();
Comparisons for the class

C/C++: let is like const auto; let mut is like plain auto. Python: every name is rebindable, so Python code works like Rust code that shadows everything; the difference is that Rust checks the types of each new binding.

Integer types and overflow

In debug builds, arithmetic overflow panics (attempt to add with overflow). In release builds, the default is two's-complement wrapping, controlled by the overflow-checks profile setting. Neither is undefined behaviour. Explicit methods: checked_* returns Option, wrapping_* wraps, saturating_* clamps, overflowing_* returns the value and a flag. Conversions are always explicit: as casts (can truncate), or From/TryFrom (Session 3).

char is a Unicode scalar value, always 4 bytes, so 'é' and 'R' are the same size. Strings are UTF-8 and covered in Session 2, which is why the lab only uses string literals.

Expressions and the unit type

A block's value is its final expression. A trailing semicolon discards the value and the block evaluates to (), the unit type (a zero-sized type with one value). The error expected i32, found () almost always means a stray semicolon, and rustc says so: "remove this semicolon to return this value".

Control flow

if requires a bool. loop is the only loop that can produce a value through break value, because it's the only one the compiler knows runs until a break. for works with anything that implements IntoIterator; ranges and arrays are the week 1 examples, and iterators get a full treatment in Session 4. Labelled breaks ('outer:) exit nested loops.

fmt and clippy

clippy ships hundreds of lints in groups (correctness, suspicious, style, complexity, perf, pedantic). Correctness lints are errors by default. The course grader runs cargo clippy -- -D warnings, which turns every warning into an error. In the pi demo, the lint is clippy::approx_constant.

Lab solution: Robbie's Greeting

Also in labs/lab1-robbie-greeting, with two tests. It passes cargo test, cargo clippy -- -D warnings and cargo fmt --check.

//! Lab 1: Robbie's Greeting. A boot log, a countdown and a hello.
use std::thread;
use std::time::Duration;

const MODEL: &str = "Robbie v11";
const PARTS: [&str; 5] = ["optics", "cassette deck", "shoulders", "grippers", "tracks"];

/// One line of the boot log, padded so the OKs line up.
fn boot_line(step: usize, total: usize, part: &str) -> String {
    format!("[{step}/{total}] checking {part:<14} OK")
}

/// Battery drops 7% per part checked, but never below zero.
fn battery_after(checks: u32) -> u32 {
    100_u32.saturating_sub(checks * 7)
}

fn main() {
    println!("== {MODEL} boot sequence ==");
    let total = PARTS.len();
    for (i, part) in PARTS.iter().enumerate() {
        println!("{}", boot_line(i + 1, total, part));
        thread::sleep(Duration::from_millis(150));
    }

    let battery = battery_after(total as u32);
    let mood = if battery > 50 { "chipper" } else { "sleepy" };
    println!("battery {battery}% and feeling {mood}");

    for n in (1..=3).rev() {
        println!("{n}...");
        thread::sleep(Duration::from_millis(300));
    }
    println!("Hello, world! I am {MODEL}. Let's learn some Rust.");
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn boot_line_pads_parts() {
        assert_eq!(
            boot_line(1, 5, "optics"),
            "[1/5] checking optics         OK"
        );
    }

    #[test]
    fn battery_never_goes_negative() {
        assert_eq!(battery_after(5), 65);
        assert_eq!(battery_after(100), 0);
    }
}
Discussion prompts
  • Why does boot_line take usize for the step? (Because enumerate gives indexes as usize.)
  • What happens if you change saturating_sub to - and check 20 parts? (A panic in debug: unsigned subtraction overflow.)
  • Why is total as u32 needed? (No implicit conversions between integer types.)

//! Robbie's Units Converter. Fill in every `todo!()` so `cargo test` passes.

/// Kilometres in one mile.
pub const KM_PER_MILE: f64 = 1.609_344;

/// Converts kilometres to miles.
pub fn km_to_miles(km: f64) -> f64 {
    km / KM_PER_MILE
}

/// Converts miles to kilometres.
pub fn miles_to_km(miles: f64) -> f64 {
    miles * KM_PER_MILE
}

/// Converts degrees Celsius to degrees Fahrenheit.
pub fn celsius_to_fahrenheit(c: f64) -> f64 {
    c * 9.0 / 5.0 + 32.0
}

/// Converts degrees Fahrenheit to degrees Celsius.
pub fn fahrenheit_to_celsius(f: f64) -> f64 {
    (f - 32.0) * 5.0 / 9.0
}

/// Draws a 10-cell battery bar. Values over 100 are treated as 100.
///
/// `battery_bar(42)` returns `"[####------] 42%"` (each `#` is 10%, rounded down).
pub fn battery_bar(percent: u8) -> String {
    let p = percent.min(100);
    let filled = (p / 10) as usize;
    let mut bar = String::from("[");
    for i in 0..10 {
        if i < filled {
            bar.push('#');
        } else {
            bar.push('-');
        }
    }
    bar.push_str("] ");
    format!("{bar}{p}%")
}

/// Robbie's mood for a battery level: "sleepy" under 20, "ok" under 80, "zoomy" otherwise.
pub fn battery_mood(percent: u8) -> &'static str {
    if percent < 20 {
        "sleepy"
    } else if percent < 80 {
        "ok"
    } else {
        "zoomy"
    }
}

Hidden tests the grader adds: battery_bar(0) is "[----------] 0%"; battery_bar(100) and battery_bar(255) are full and show 100%; battery_bar(9) has no #; battery_mood(19) is sleepy and battery_mood(79) is ok; km_to_miles(0.0) is 0; Celsius and Fahrenheit round-trip for -273.15, 0 and 37.

Extensions for fast students

  • Add ANSI colours to the boot log ("\x1b[32mOK\x1b[0m"), then discuss why a library like colored exists.
  • Read a name with std::io::stdin().read_line and greet the user. (Preview of String for Session 2.)
  • Make the countdown length a const and add a labelled loop that aborts the boot if the battery drops under 50%.
