Learning goals

By the end of Session 4 a student can:

  1. Use Vec and HashMap, including get, sorting, and the entry API, and explain why pushing while borrowing fails.
  2. Define a trait with required and default methods, implement it for several types, and derive the standard traits.
  3. Write generic functions and structs with trait bounds and where clauses.
  4. Choose between a generic and Box<dyn Trait>.
  5. Write closures, and tell Fn, FnMut and FnOnce apart.
  6. Replace loops with iterator chains, and explain laziness.
  7. Read and write lifetime annotations on functions and structs.

Deeper notes by topic

Vec and HashMap

The E0502 demo is the most important minute of the first hour: it shows the borrow checker preventing a real bug (iterator invalidation in C++). Have students fix it two ways. For HashMap, stress that iteration order is random per run, by design, to resist hash-flooding attacks. Tests that compare a printed HashMap will flake; sort first or use BTreeMap.

Traits

Traits are the session's centre. Map them to what the room knows: interfaces (Java, C#, Go), protocols (Swift), duck typing checked at compile time (Python). There is no inheritance; default methods plus traits cover most of what inheritance is used for. The orphan rule (you can implement a trait for a type only if you own one of them) will come up if anyone tries impl Display for Vec<T>; one sentence is enough.

Generics and trait objects

Monomorphization means generics are zero-cost but grow the binary; dyn means one copy of the code and a vtable lookup per call. Neither is "better". The homework deliberately uses both so students see where each fits. Box is used before Session 5 explains it; "a pointer to something on the heap" is all they need today.

Closures

The capture rules mirror ownership: a closure borrows what it reads, mutably borrows what it changes, and moves what it consumes. move forces ownership. Session 5's thread::spawn(move || ...) is the payoff, so plant it now.

Iterators

Show the Iterator trait itself: one required method, next(&mut self) -> Option<Self::Item>, and dozens of default methods. That ties traits, default methods and Option together nicely. The |&&r| pattern in filter confuses everyone; .copied() earlier in the chain makes it go away.

Lifetimes

The key sentence: a lifetime annotation describes, it never extends. Elision rules cover most code. If a student writes 'static to silence an error, that's usually wrong; ask them which input the answer comes from.

Lab solution: Robbie's Mission Planner

The full file is teacher/s4/lab4-solution-lib.rs; drop it in as labs/lab4-mission-planner/src/lib.rs and all nine tests pass, with clippy and fmt clean.

//! Lab 4: Robbie's Mission Planner.
//!
//! Robbie has a to-do list for the studio and only so much battery. You'll use
//! iterators, closures and a HashMap to turn the list into a plan.
use std::collections::HashMap;

/// One job on Robbie's list.
#[derive(Debug, Clone, PartialEq)]
pub struct Task {
    pub name: String,
    pub room: String,
    pub minutes: u32,
    /// 1 (whenever) to 5 (right now)
    pub priority: u8,
    pub done: bool,
}

impl Task {
    /// A shortcut for building tasks in tests and in main.
    pub fn new(name: &str, room: &str, minutes: u32, priority: u8) -> Task {
        Task {
            name: name.to_string(),
            room: room.to_string(),
            minutes,
            priority,
            done: false,
        }
    }
}

/// Step 1. The total minutes of every task that isn't done yet.
pub fn minutes_left(tasks: &[Task]) -> u32 {
    tasks.iter().filter(|t| !t.done).map(|t| t.minutes).sum()
}

/// Step 2. The tasks that aren't done, most urgent first.
/// Higher priority comes first; for equal priority, shorter tasks first;
/// for equal priority and minutes, alphabetical by name.
pub fn todo_list(tasks: &[Task]) -> Vec<&Task> {
    let mut list: Vec<&Task> = tasks.iter().filter(|t| !t.done).collect();
    list.sort_by(|a, b| {
        b.priority
            .cmp(&a.priority)
            .then(a.minutes.cmp(&b.minutes))
            .then(a.name.cmp(&b.name))
    });
    list
}

/// Step 3. Minutes still to do in each room. Rooms with nothing left to do
/// don't appear at all.
pub fn minutes_by_room(tasks: &[Task]) -> HashMap<String, u32> {
    let mut rooms = HashMap::new();
    for t in tasks.iter().filter(|t| !t.done) {
        *rooms.entry(t.room.clone()).or_insert(0) += t.minutes;
    }
    rooms
}

/// Step 4. Plan a shift: walk the todo_list in order and take every task that
/// still fits in the minutes left. A task that doesn't fit is skipped, and the
/// planner keeps looking for shorter ones. Returns the names in the order taken.
pub fn plan(tasks: &[Task], budget: u32) -> Vec<&str> {
    let mut left = budget;
    let mut names = Vec::new();
    for t in todo_list(tasks) {
        if t.minutes <= left {
            left -= t.minutes;
            names.push(t.name.as_str());
        }
    }
    names
}

/// Step 5. The first task in `room` that isn't done, if there is one.
/// The answer borrows from `tasks`, not from `room`, and the lifetime says so.
pub fn next_in_room<'a>(tasks: &'a [Task], room: &str) -> Option<&'a Task> {
    tasks.iter().find(|t| !t.done && t.room == room)
}

Praise: one-chain answers for steps 1 and 5; .then() for tie-breakers; using todo_list inside plan instead of sorting twice. Redirect: cloning Tasks into the result of todo_list (the signature asks for references), and break in plan at the first task that doesn't fit (the doc says keep looking for shorter ones; the step 4 test checks it).

/// Rules for Robbie:
/// - name is "Robbie", kind is "studio robot"
/// - power is 120 W, plus 1 W for every percent of rust (rusty joints work harder)
/// - label: the usual label, but when he is 50% rust or more, add " squeak" at the end,
///   like "Robbie (studio robot, 170 W) squeak"
impl Bot for Robbie {
    fn name(&self) -> &str {
        "Robbie"
    }
    fn kind(&self) -> &'static str {
        "studio robot"
    }
    fn power(&self) -> u32 {
        120 + u32::from(self.rust)
    }
    fn label(&self) -> String {
        let plain = format!("{} ({}, {} W)", self.name(), self.kind(), self.power());
        if self.rust >= 50 {
            plain + " squeak"
        } else {
            plain
        }
    }
}

/// Rules for a drone: kind is "drone", power is 15 W per rotor.
impl Bot for Drone {
    fn name(&self) -> &str {
        &self.name
    }
    fn kind(&self) -> &'static str {
        "drone"
    }
    fn power(&self) -> u32 {
        15 * self.rotors
    }
}

/// Rules for a vacuum: kind is "vacuum", power is 40 W, or 55 W when the bin is full.
impl Bot for Vacuum {
    fn name(&self) -> &str {
        &self.name
    }
    fn kind(&self) -> &'static str {
        "vacuum"
    }
    fn power(&self) -> u32 {
        if self.bin_full { 55 } else { 40 }
    }
}

    /// Park a bot.
    /// - Names are compared ignoring case: "zippy" and "Zippy" are the same bot.
    ///   A name that's already parked gives `Duplicate`, with the new bot's name.
    /// - A bot that needs more than `available()` watts gives `OverBudget`.
    ///   Using exactly the watts left is fine.
    /// - The name check comes first.
    /// - A refused bot changes nothing.
    pub fn park(&mut self, bot: Box<dyn Bot>) -> Result<(), GarageError> {
        if self.position(bot.name()).is_some() {
            return Err(GarageError::Duplicate(bot.name().to_string()));
        }
        let available = self.available();
        if bot.power() > available {
            return Err(GarageError::OverBudget {
                needed: bot.power(),
                available,
            });
        }
        self.bots.push(bot);
        Ok(())
    }

    /// Take a bot out of the garage by name (ignoring case) and hand it back.
    /// The other bots keep their order. No such bot gives `NotFound` with the name asked for.
    pub fn unpark(&mut self, name: &str) -> Result<Box<dyn Bot>, GarageError> {
        let i = self
            .position(name)
            .ok_or_else(|| GarageError::NotFound(name.to_string()))?;
        Ok(self.bots.remove(i))
    }

    /// The names of the parked bots, in alphabetical order.
    pub fn names(&self) -> Vec<&str> {
        let mut names: Vec<&str> = self.bots.iter().map(|b| b.name()).collect();
        names.sort();
        names
    }

    /// How many bots of each kind are parked, like {"drone": 2, "vacuum": 1}.
    pub fn count_by_kind(&self) -> HashMap<&'static str, usize> {
        let mut counts = HashMap::new();
        for b in &self.bots {
            *counts.entry(b.kind()).or_insert(0) += 1;
        }
        counts
    }

    /// Labels of the bots drawing at least `watts`, in the order they were parked.
    pub fn power_hogs(&self, watts: u32) -> Vec<String> {
        self.bots
            .iter()
            .filter(|b| b.power() >= watts)
            .map(|b| b.label())
            .collect()
    }

    fn position(&self, name: &str) -> Option<usize> {
        self.bots
            .iter()
            .position(|b| b.name().eq_ignore_ascii_case(name))
    }
}
/// The largest item in a slice, or None when it's empty.
/// Works for any type that can be compared and copied: numbers, chars, bools.
pub fn largest<T: PartialOrd + Copy>(items: &[T]) -> Option<T> {
    let mut best = *items.first()?;
    for &item in items {
        if item > best {
            best = item;
        }
    }
    Some(best)
}

/// The bot that draws the most power from a slice of one kind of bot.
/// When two draw the same, the first one wins. None for an empty slice.
pub fn hungriest<B: Bot>(bots: &[B]) -> Option<&B> {
    let mut best = bots.first()?;
    for b in bots {
        if b.power() > best.power() {
            best = b;
        }
    }
    Some(best)
}
