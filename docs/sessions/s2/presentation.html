The memory question

Who cleans up?

LanguageWho frees memoryThe catch
CYou, with free()Forget it: leak. Do it twice: crash. Use it after: chaos.
C++Destructors and smart pointersSafe if you follow the rules; the compiler doesn't make you.
PythonA garbage collectorPauses, overhead, and no say in when.
RustThe owner, automaticallyThe compiler checks the rules before the program runs.
C++ folks will say "that's just RAII". They're right, and that's a compliment to C++. The difference is that Rust enforces it: you can't accidentally keep a pointer to freed memory, because the program won't compile.

Stack and heap

Two places to keep things

The stack is a stack of plates: fast, tidy, last on is first off. Everything on it has a size known at compile time: i32, bool, [u8; 4].

The heap is a warehouse. You ask for space, get back an address, and can grow later. A String or Vec keeps its contents there.

   stack (s)              heap
 ┌──────────┬─────┐     ┌───┬───┬───┬───┬───┬───┐
 │ ptr      │  ●──┼────▶│ r │ o │ b │ b │ i │ e │
 │ len      │  6  │     └───┴───┴───┴───┴───┴───┘
 │ capacity │  6  │
 └──────────┴─────┘
The key picture for the whole session. A String is three numbers on the stack and the real text on the heap. Every rule today is about making sure exactly one of those stack records is responsible for freeing that heap memory.

The rules

Ownership in three lines

  1. Every value has exactly one owner.
  2. There can only be one owner at a time.
  3. When the owner goes out of scope, the value is dropped.
Remember this

One wrench, one mechanic. Whoever holds the wrench is responsible for putting it back. You can hand it over, or lend it out, but there's never a moment when two people both think it's theirs.

Write the three rules on the board and leave them there all session. Every compiler error in the lab maps to one of them.

Rule 3 in action

Drop at the closing brace

fn main() {
    let outer = String::from("chassis");
    {
        let inner = String::from("antenna");
        println!("{outer} and {inner}");
    } // inner is dropped here: its heap memory is freed
    println!("{outer} is still here");
} // outer is dropped here

No free(), no garbage collector. The compiler inserts the cleanup exactly where the owner's scope ends.

Ask: where is inner's memory freed? Students usually say "at the end of main". Correct them gently: at its own closing brace. Then mention that Rust calls this function drop, and later in the course they'll write their own.

Rule 2 in action

A move

This one fails on purpose. Press Run and read the error.

fn main() {
    let a = String::from("wrench");
    let b = a;
    println!("{a}");
}

let b = a doesn't copy the text. It hands the wrench to b. Now a is an empty name tag, and Rust won't let you use it: error[E0382]: borrow of moved value: `a`.

Draw it: two stack records pointing at one heap block would mean two owners, and both would free the same memory at the end of main: a double free. Rust prevents it by making a the "moved-from" husk. C++ folks: this is like std::move, except the compiler stops you using the husk.

Moves happen in function calls too

Passing is giving

fn inspect(part: String) {
    println!("inspecting {part}");
} // part is dropped here

fn main() {
    let arm = String::from("left arm");
    inspect(arm);
    // println!("{arm}"); // uncomment me: arm was moved into inspect
}

Calling inspect(arm) moves the String into the function. When inspect ends, the arm is gone. Robbie is now one arm short.

Have students uncomment the println and run it. Then ask: how would we keep the arm? Two answers appear: return it back (clumsy), or lend it (borrowing, three slides from now).

Copy vs Clone

Why numbers don't move

fn main() {
    let x = 5;
    let y = x; // Copy: x is still fine
    println!("{x} {y}");

    let s = String::from("bolt");
    let t = s.clone(); // Clone: a full second copy on the heap
    println!("{s} {t}");
}
  • Copy types live entirely on the stack and are cheap to duplicate: all integers, floats, bool, char, and tuples or arrays of them.
  • Clone is an explicit, possibly expensive deep copy. You have to ask for it, so you can see the cost.
Remember this

Copy is a photocopy, Clone is a 3D print. A photocopy of a number is instant. A 3D print of a whole String takes time and material, so Rust makes you press the button yourself.

Warn about clone-itis: beginners sprinkle .clone() until the errors stop. It works, but it hides the design. The lab forbids clone on purpose.

Borrowing

Lend it with &

fn measure(part: &String) -> usize {
    part.len()
} // part is a borrow, so nothing is dropped here

fn main() {
    let arm = String::from("left arm");
    let n = measure(&arm);
    println!("{arm} has {n} letters"); // arm is still ours
}

&arm makes a reference: a pointer that promises not to outlive or free the value. The function borrows the arm, measures it and hands it back automatically.

The & on the call and the & on the parameter type go together. Mention that you'll improve &String to &str in a few slides; leave that hook dangling on purpose.

Changing what you borrowed

&mut: the exclusive loan

fn recharge(level: &mut u32) {
    *level += 30;
}

fn main() {
    let mut battery = 40;
    recharge(&mut battery);
    println!("battery: {battery}");
}

Three things must line up: the variable is mut, the call passes &mut, and the parameter type is &mut. The * means "the thing this points at".

C folks will feel at home with *level. Python folks: this is how you get "pass by reference" on purpose, and the &mut at the call site means you can always see which calls might change your variable.

The borrowing rule

Many readers, or one writer

At any moment you can have any number of & or exactly one &mut. Never both.

Remember this

Library rule: lots of people can read the book, but only one can write in it, and nobody reads while they're writing. That one rule is why Rust programs don't have data races.

This is the rule behind E0499 (two &mut) and E0502 (a & and a &mut overlapping). Both show up in the lab. Point out that this is a compile-time check: there's no lock, no runtime cost.

When a borrow ends

At its last use, not at the brace

fn main() {
    let mut parts = vec![String::from("head"), String::from("arm")];
    let first = &parts[0];
    println!("first: {first}"); // last use of first: the borrow ends here
    parts.push(String::from("tread")); // so this is fine
    println!("{parts:?}");
}

Swap the println! and the push and it fails: push might move the whole vector somewhere bigger, leaving first pointing at nothing.

This is called non-lexical lifetimes. The compiler tracks where each borrow is last used. Do the swap live and show E0502. That exact mistake is lab puzzle 4.

Dangling references

Rust won't hand you a ghost

Fails on purpose.

fn make_callsign() -> &String {
    let sign = String::from("ROBBIE-007");
    &sign
} // sign is dropped here, so the reference would point at nothing

fn main() {
    println!("{}", make_callsign());
}

The fix is to return the String itself. Ownership moves out to the caller, and nothing dangles.

The error message mentions a "lifetime specifier". Tell students not to panic: lifetimes are just the compiler's name for "how long a borrow is valid". In C this compiles and returns a pointer to dead stack memory.

Slices

Borrow just part of it

fn main() {
    let cmd = String::from("rotate left 90");
    let verb = &cmd[0..6];
    let rest = &cmd[7..];
    println!("verb={verb} rest={rest}");

    let readings = [12, 15, 11, 18, 20];
    let middle = &readings[1..4];
    println!("{middle:?}");
}

A slice is a pointer plus a length, borrowed from something else. &str is a string slice; &[i32] is a slice of numbers.

Gotcha

String slice positions are bytes, not letters. "héllo" has an é that takes two bytes, so &s[0..2] panics. Stick to ASCII text for slicing by number, or use .chars().

The two-dots-stop-short rule from Session 1 applies here. Demo the é panic only if time allows; it's in the handbook.

String vs &str

The owner and the window

String&str
Owns its text?Yes, on the heapNo, it borrows
Can grow?Yes: push_str, pushNo
Literal "hi" isA &'static str, baked into the program
Use for parametersOnly if you need to keep itAlmost always
 
fn shout(text: &str) -> String {
    format!("{}!", text.to_uppercase())
}

fn main() {
    let owned = String::from("low battery");
    println!("{}", shout(&owned)); // &String turns into &str
    println!("{}", shout("rust alert")); // a literal is already &str
}
This is the payoff for the hook on the borrowing slide: take &str, and callers can pass either. Clippy even has a lint, ptr_arg, that nags you if you write &String as a parameter.

A first look at lifetimes

When the compiler asks "borrowed from where?"

fn longer<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

fn main() {
    let x = String::from("servo");
    let y = String::from("actuator");
    println!("{}", longer(&x, &y));
}

'a is a label that says "the result is borrowed from the inputs, so it can't outlive them". Most of the time Rust works this out on its own. You only write it when there's more than one input reference and a reference comes back out.

Keep this light. Lifetimes get their own deep dive in Session 4. Today the goal is just: the apostrophe isn't scary, it's a name for "how long this borrow is good for".
