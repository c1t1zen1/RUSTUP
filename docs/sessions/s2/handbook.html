1. Why ownership exists

Every program borrows memory from the computer and has to give it back. Give it back too early and something still using it reads garbage. Give it back twice and the program crashes. Never give it back and memory slowly fills up. These three bugs (use after free, double free and leaks) have caused a huge share of the security holes in C and C++ software.

Python and JavaScript solve it with a garbage collector that tidies up while your program runs. Rust solves it before your program runs: a set of rules, checked by the compiler, that guarantees every piece of memory is freed exactly once, at a point you can see in the code.

Remember this

One wrench, one mechanic. Whoever holds the wrench is responsible for putting it back on the wall. You can hand it over or lend it out, but there's never a moment when two people both think it's theirs.

2. Stack and heap

The stack is a pile of plates. Every function call puts a plate on top with its local variables, and takes it off when it returns. It's fast because it never has to search for space, but everything on it must have a size known when the program compiles.

The heap is a warehouse. When you need space for something that can grow, like a String or a Vec, you ask the warehouse for room and get back an address. Finding room is slower, and somebody has to give it back.

   stack (s)              heap
 ┌──────────┬─────┐     ┌───┬───┬───┬───┬───┬───┐
 │ ptr      │  ●──┼────▶│ r │ o │ b │ b │ i │ e │
 │ len      │  6  │     └───┴───┴───┴───┴───┴───┘
 │ capacity │  6  │
 └──────────┴─────┘

A String is three numbers on the stack: where the text is, how long it is, and how much room it has. Ownership is all about making sure exactly one of those stack records frees that heap text.

3. The three rules

  1. Every value has exactly one owner.
  2. There can only be one owner at a time.
  3. When the owner goes out of scope, the value is dropped (its memory is freed).
fn main() {
    let outer = String::from("chassis");
    {
        let inner = String::from("antenna");
        println!("{outer} and {inner}");
    } // inner is dropped here
    println!("{outer} is still here");
} // outer is dropped here
Coming from C, C++ or Python

In C you'd call free(inner) yourself. In C++ this is RAII, and a destructor runs at the brace. In Python the garbage collector frees it at some later point. Rust works like C++ here, except the compiler also stops you from keeping a pointer to inner after it's gone.

4. Move, Copy and Clone

Move

Assigning a String to another variable, or passing it to a function, moves it. The new variable owns it; the old one becomes an empty name tag you're not allowed to use.

let a = String::from("wrench");
let b = a;          // the wrench moves to b
println!("{a}");    // error[E0382]: borrow of moved value: `a`

Why not just copy the text? Because then a and b would both point at the same heap memory, and both would free it at the end: a double free. Rust prevents it by making a unusable.

Remember this

"Let b = a" means "a, give b the wrench." It doesn't mean "photocopy a". After the hand-off, a has empty hands.

Copy

Small values that live entirely on the stack are Copy: assigning them makes a cheap duplicate and both stay usable. That's every integer and float, bool, char, and tuples and arrays made only of Copy things.

fn main() {
    let x = 5;
    let y = x;
    println!("{x} {y}"); // both fine: i32 is Copy
}

Clone

If you really do want two independent Strings, ask for it with .clone(). It copies the heap data too, so it costs time and memory, and Rust makes you write it so you can see that cost.

fn main() {
    let s = String::from("bolt");
    let t = s.clone();
    println!("{s} {t}");
}
Remember this

Copy is a photocopy, Clone is a 3D print. Photocopying a number is instant, so Rust does it for you. 3D printing a whole String takes time and plastic, so you have to press the button.

Gotcha

Clone-itis. When the compiler complains, it's tempting to add .clone() until it stops. It works, but it hides the real question: who should own this? Reach for a borrow first. Clone when you genuinely need two copies.

Moving into functions

fn inspect(part: String) {
    println!("inspecting {part}");
} // part is dropped here

fn main() {
    let arm = String::from("left arm");
    inspect(arm);
    // arm has been moved into inspect. Using it here would be E0382.
}

Passing a String to a function gives it away. When the function ends, it's dropped. Robbie lost an arm that way once. Let's not.

5. Borrowing

A reference, written &, lets a function use a value without owning it. The owner keeps it, and the reference is guaranteed never to outlive it.

fn measure(part: &str) -> usize {
    part.len()
}

fn main() {
    let arm = String::from("left arm");
    let n = measure(&arm);
    println!("{arm} has {n} letters"); // still ours
}

Mutable borrowing

To change something you borrowed, you need a mutable reference, &mut. Three things must line up: the variable is let mut, the call passes &mut, and the parameter type is &mut. Use * to reach the value behind it.

fn recharge(level: &mut u32) {
    *level += 30;
}

fn main() {
    let mut battery = 40;
    recharge(&mut battery);
    println!("battery: {battery}");
}
Remember this

& is "look, don't touch". &mut is "touch, but you're alone in the room".

6. Many readers or one writer

This is the rule the borrow checker enforces. At any moment, a value can have any number of shared references (&) or exactly one mutable reference (&mut), but not both.

Remember this

Library rule. Lots of people can read the same book. Only one person can write in it, and nobody reads over their shoulder while they do. That rule, checked at compile time, is why safe Rust has no data races.

A borrow lasts until its last use, not until the closing brace. So reordering lines fixes many errors:

fn main() {
    let mut parts = vec![String::from("head"), String::from("arm")];
    let first = &parts[0];
    println!("first: {first}"); // last use of first
    parts.push(String::from("tread")); // fine: the borrow is over
    println!("{parts:?}");
}
Gotcha

Put that println! after the push and you get E0502. Why does Rust care? push may need a bigger warehouse slot, so it moves every part somewhere new. first would still point at the old, empty spot. In C++ that's a classic iterator-invalidation bug; in Rust it's a compile error.

7. Slices

A slice borrows a run of elements from something else: a pointer to the start and a length. &str is a slice of a string, &[T] is a slice of an array or vector.

fn main() {
    let cmd = String::from("rotate left 90");
    let verb = &cmd[0..6];
    let rest = &cmd[7..];
    println!("verb={verb} rest={rest}");

    let readings = [12, 15, 11, 18, 20];
    let middle = &readings[1..4];
    println!("{middle:?}");
}

[..4] means "from the start", [7..] means "to the end", and [..] is the whole thing. Two dots still stop short.

Gotcha

String slice positions count bytes, not letters. In "héllo" the é takes two bytes, so &s[0..2] cuts it in half and panics. For plain English text this never bites; for anything else, use .chars().

8. String vs &str

String&str
Owns its textYes, on the heapNo, it's a borrowed view
Can growYes: push, push_strNo
A literal "hi"Is a &'static str, stored inside your program
Best forBuilding and keeping textFunction parameters, almost always
 
fn shout(text: &str) -> String {
    format!("{}!", text.to_uppercase())
}

fn main() {
    let owned = String::from("low battery");
    println!("{}", shout(&owned)); // &String becomes &str automatically
    println!("{}", shout("rust alert")); // a literal already is one
}
Remember this

String is the house, &str is the window. You own the house and can build an extension. Through a window you can only look, but every house has windows, so a function that asks for a window works with any house, and with a postcard (a literal) too.

9. Lifetimes, gently

A lifetime is the compiler's name for "how long a borrow stays valid". Rust works most of them out on its own. You only write one when a function takes more than one reference and returns a reference, so the compiler needs to know which input the answer is borrowed from.

fn longer<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

fn main() {
    let x = String::from("servo");
    let y = String::from("actuator");
    println!("{}", longer(&x, &y));
}

Read 'a aloud as "for as long as both inputs live". It doesn't change how long anything lives; it just describes it so the compiler can check it. Session 4 goes deeper.

Gotcha

You can never return a reference to something created inside the function. It's dropped when the function ends, so the reference would point at nothing (E0106). Return the owned value instead: fn make() -> String, not -> &String.

Practice questions

1. After let a = String::from("x"); let b = a;, can you print a?

No. The String moved into b; using a is E0382.

2. After let a = 7; let b = a;, can you print a?

Yes. Integers are Copy, so b got its own duplicate.

3. Why can't String be Copy?

It owns heap memory. A silent copy would mean two owners freeing the same memory: a double free.

4. What's wrong with fn recharge(level: &u32) { *level += 1; }?

You can't change a value through a shared &. Use &mut u32, and call it with &mut battery on a let mut battery.

5. Can you have two & borrows of the same value at once? Two &mut?

Two &: yes, as many as you like. Two &mut: no, one at a time.

6. When does a borrow end?

At its last use, not at the end of the block.

7. What is &"robbie"[1..3]?

"ob": bytes 1 and 2.

8. Why is &str a better parameter type than &String?

Callers can pass a &String, a slice, or a literal. With &String a literal won't fit.

9. Why does fn f() -> &String { let s = String::new(); &s } fail?

s is dropped when f returns, so the reference would dangle. Return String.

10. What does 'a in fn longer<'a>(a: &'a str, b: &'a str) -> &'a str promise?

That the returned slice is borrowed from the inputs and won't be used after either of them is gone.
