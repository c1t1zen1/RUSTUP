The big idea

Leaving the guard rails, on purpose

For five sessions the compiler has checked everything. Today you meet the places where it can't: code that writes code, raw memory, other languages, and the outside world.

Good Rust doesn't avoid these. It keeps them small, puts a safe wrapper around them, and writes down why they're fine.

Remember this

Unsafe on the inside, safe on the outside. The standard library is full of unsafe code you've used every day: Vec, String, split_at_mut. You never had to write unsafe to call them.

Coming from C or C++: everything there is unsafe Rust, all the time. Coming from Python: the interpreter is a big unsafe C program with a safe wrapper; that's the same pattern. The goal today is judgment: when is it justified, and how small can you make it.

Macros

Code that writes code

// A macro matches the shape of what you pass it, then writes code.
macro_rules! squeak {
    () => {
        println!("squeak")
    };
    ($times:expr) => {
        for _ in 0..$times {
            println!("squeak")
        }
    };
}

fn main() {
    squeak!(); // matches the first arm
    squeak!(2); // matches the second, with $times = 2
}
  • macro_rules! makes a declarative macro: a list of arms, like match, but on the shape of the code you pass in.
  • $times:expr means "an expression, call it $times". Others: ident, ty, tt, literal.
  • The ! tells the reader it's a macro: println!, vec! and assert_eq! are all macros.
Why a macro and not a function? A function can't take a variable number of arguments, can't take a format string checked at compile time, and can't write a for loop around your code. Rule of thumb: try a function first, then a generic function, then a macro.

Repetition

Any number of arguments

// $( ... ),* matches a comma-separated list, and repeats the code for each.
macro_rules! parts_list {
    ($($part:expr),* $(,)?) => {
        vec![$(String::from($part)),*]
    };
}

fn main() {
    let spares = parts_list!["bolt", "spring", "left elbow"];
    println!("{spares:?}");
    let none: Vec<String> = parts_list![];
    println!("{} spares in the empty box", none.len());
}

$( ... ),* matches zero or more items separated by commas. Inside the arm, $( ... ),* repeats the code once per item. + means one or more, ? means zero or one.

// A macro can call itself, peeling one item off each time.
macro_rules! loudest {
    ($x:expr) => { $x };
    ($x:expr, $($rest:expr),+) => {
        std::cmp::max($x, loudest!($($rest),+))
    };
}

fn main() {
    println!("loudest squeak: {}", loudest!(42, 87, 63, 12));
}
This is exactly how vec! works. The recursive one peels off the first item and calls itself on the rest; it's in Lab 6 step 1. The $(,)? at the end of the first pattern allows a trailing comma, a nice touch for users.

When a macro doesn't match

No arm, no code

Fails on purpose (no arm matches). Press Run and read the error.

macro_rules! squeak {
    () => {
        println!("squeak")
    };
}

fn main() {
    squeak!(3); // no arm takes an argument
}

The error says "no rules expected this token". Read it like a failed match: none of the arms has that shape. Add an arm, or change the call.

Remember this

A macro is a match on code. Arms are tried top to bottom, and the first one that fits wins.

Macro errors are the least friendly in Rust. cargo expand (a cargo plugin) shows the code a macro wrote; mention it, don't install it in class. Procedural macros, the derive kind like #[derive(Serialize)], are a whole separate crate type: out of scope today, but students have used them since Session 3.

unsafe

Five things the compiler can't check

Fails on purpose (E0133). Press Run and read the error.

fn main() {
    let battery = 87;
    let p = &battery as *const i32; // making a raw pointer is safe
    println!("{}", *p); // reading through it is not
}

Making a raw pointer is fine. Following it isn't, because the compiler can't prove it points at something alive (E0133). An unsafe block unlocks five abilities and nothing more:

  • Follow a raw pointer (*const T, *mut T).
  • Call an unsafe fn, including C functions.
  • Use a static mut, implement an unsafe trait, read a union field.
The borrow checker still runs inside unsafe. Unsafe doesn't turn checks off; it lets you do five extra things, and you promise they're fine. If the promise is wrong, the result is undefined behaviour: the program can do anything, including look fine until Friday.

Keeping a promise

Every unsafe block gets a SAFETY comment

fn main() {
    let mut battery = 87;
    let p = &mut battery as *mut i32;
    // SAFETY: p came from a live, unique &mut just above, and nothing else
    // touches battery while we use it.
    unsafe {
        *p -= 10;
        println!("battery through a raw pointer: {}", *p);
    }
    println!("battery: {battery}");
}
Remember this

If you can't write the SAFETY comment, you can't write the block. Say which rule you're promising to follow, and why it holds right here.

clippy has a lint, undocumented_unsafe_blocks, that enforces SAFETY comments; many real projects turn it on. The code review in the final project looks for them too. In this example the raw pointer is pointless (a &mut would do), which is the point: most of the time you don't need unsafe at all.

A real reason

Two halves, both changeable

Fails on purpose (E0499). Press Run and read the error.

fn main() {
    let mut joints = [5, 9, 2, 7];
    let left = &mut joints[..2];
    let right = &mut joints[2..]; // the halves don't overlap, but Rust can't tell
    left[0] = 0;
    right[0] = 0;
    println!("{joints:?}");
}

The two halves can't overlap, but the borrow checker only sees "two &mut into joints" (E0499). The standard library has a safe function for exactly this:

fn main() {
    let mut joints = [5, 9, 2, 7];
    let (left, right) = joints.split_at_mut(2); // std did the unsafe part for you
    left[0] = 0;
    right[0] = 0;
    println!("{joints:?}");
}
Always look for the safe std function first: split_at_mut, chunks_mut, swap, mem::take. The next slide shows how split_at_mut is built, which is what Lab 6 step 2 asks for. That's the one time students write it themselves.

Building the safe wrapper

Unsafe inside, safe outside

/// Two halves you can change at once. Safe to call, unsafe inside.
fn split_halves(items: &mut [u32]) -> (&mut [u32], &mut [u32]) {
    let len = items.len();
    let mid = len / 2;
    let ptr = items.as_mut_ptr();
    // SAFETY: ptr is valid for len items. 0..mid and mid..len never overlap,
    // and both slices live no longer than the borrow of items.
    unsafe {
        (
            std::slice::from_raw_parts_mut(ptr, mid),
            std::slice::from_raw_parts_mut(ptr.add(mid), len - mid),
        )
    }
}

fn main() {
    let mut joints = [5, 9, 2, 7, 4];
    let (left, right) = split_halves(&mut joints);
    left[0] = 0;
    right[0] = 0;
    println!("{joints:?}");
}
  • as_mut_ptr gives a raw pointer to the first item. ptr.add(mid) moves it along.
  • from_raw_parts_mut builds a slice from a pointer and a length. That's the unsafe call.
  • The signature ties both halves to the borrow of items, so callers stay fully checked.
Walk through the SAFETY comment line by line: valid pointer, no overlap, lifetimes bounded by the input. If any of those were false, say mid could be bigger than len, it would be undefined behaviour. That's why mid comes from len / 2 and not from the caller. Lab 6 step 2.

FFI

Calling C

use std::ffi::{CStr, c_char};

// Rust 2024: an extern block is unsafe, because Rust can't check what's in C.
unsafe extern "C" {
    safe fn abs(x: i32) -> i32; // `safe`: you promise it's fine with any i32... almost
    fn strlen(s: *const c_char) -> usize; // a raw pointer, so calling it stays unsafe
}

fn c_strlen(s: &CStr) -> usize {
    // SAFETY: a &CStr always ends in a 0 byte, which is what strlen needs.
    unsafe { strlen(s.as_ptr()) }
}

fn main() {
    println!("C says |-12| = {}", abs(-12));
    println!("C says \"robbie\" has {} bytes", c_strlen(c"robbie"));
}
  • An unsafe extern "C" block declares functions that live in C. Rust can't see inside them.
  • Mark one safe fn when any arguments are fine. Otherwise each call needs unsafe.
  • c"robbie" is a C string: bytes ending in a 0, the way C expects.
FFI is Foreign Function Interface. abs and strlen come from the C standard library, which every Rust program on Linux and macOS already links. Honesty note: C's abs(INT_MIN) is undefined behaviour, so "safe fn abs" is a small lie. Lab 6 step 3 fixes it with a wrapper that returns None for i32::MIN. Ask the room to spot the lie before you tell them.

FFI, the strict version

Not marked safe? Then the call is unsafe

Fails on purpose (E0133). Press Run and read the error.

unsafe extern "C" {
    fn abs(x: i32) -> i32;
}

fn main() {
    println!("{}", abs(-12)); // not marked safe, so the call needs unsafe
}

Since Rust 2024 the extern block itself must say unsafe: you're promising the declarations match the real C functions. Each function is then safe fn or, by default, unsafe to call.

RustC
i32, u8, f64int, unsigned char, double
&CStr, CStringconst char * ending in 0
*const T, *mut Tconst T *, T *
#[repr(C)] structstruct with the same layout
For your own C code, the cc crate compiles a .c file in build.rs and links it. bindgen writes the extern block for you from a C header. Mention both; neither is needed for the final.

FFI the other way

Rust that other languages can call

// Going the other way: a Rust function that C (or Python, or Swift) can call.
#[unsafe(no_mangle)]
pub extern "C" fn robbie_battery_after(start: u32, steps: u32) -> u32 {
    start.saturating_sub(steps)
}

fn main() {
    // You can still call it from Rust like any function.
    println!("battery after 30 steps: {}", robbie_battery_after(20, 30));
}
use std::ffi::{CStr, CString};

fn main() {
    // Rust strings know their length. C strings end at a 0 byte instead.
    let name = CString::new("Robbie v11").unwrap();
    println!("{} bytes, plus the 0 at the end", name.as_bytes().len());

    let literal: &CStr = c"squeak"; // a C string literal, checked at compile time
    println!("{literal:?} back in Rust: {}", literal.to_str().unwrap());

    // A 0 byte in the middle can't be a C string.
    println!("{:?}", CString::new("rob\0bie").is_err());
}
#[unsafe(no_mangle)] keeps the name exactly as written so C can find it; in 2024 it's an unsafe attribute because two functions with the same unmangled name would clash. With crate-type = ["cdylib"] in Cargo.toml this builds a .so/.dylib/.dll that Python (ctypes), Swift or C can load. This is how Rust ends up inside Firefox, Android and the Linux kernel.

Speed

Measure in release mode, every time

cargo run                         # debug: fast to compile, slow to run, overflow checks on
cargo run --release               # optimized: often 10 to 50 times faster
cargo run --release --example bench
use std::hint::black_box;
use std::time::Instant;

fn vowels(text: &str) -> usize {
    text.bytes()
        .filter(|b| matches!(b.to_ascii_lowercase(), b'a' | b'e' | b'i' | b'o' | b'u'))
        .count()
}

fn main() {
    let text = "Robbie oils his elbows again. ".repeat(10_000);
    let mut best = u128::MAX;
    for _ in 0..10 {
        let start = Instant::now();
        black_box(vowels(black_box(&text))); // stop the optimizer skipping the work
        best = best.min(start.elapsed().as_micros());
    }
    println!(
        "{} vowels, best of 10 runs: {best} microseconds",
        vowels(&text)
    );
}

black_box hides a value from the optimizer, so it can't notice nobody uses the answer and delete the work you're timing.

The Playground runs debug builds by default (there's a Release option in its menu). For serious benchmarks people use the criterion crate, which runs many samples and gives statistics. Our home-made "best of N" with Instant is good enough to compare two versions of a function, which is Lab 6 step 4.

Overflow

Say what should happen at the edge

Compiles, then panics on purpose. Press Run and read the message.

fn main() {
    let battery: u8 = 250;
    let boost: u8 = std::hint::black_box(10);
    println!("checked:    {:?}", battery.checked_add(boost)); // None
    println!("saturating: {}", battery.saturating_add(boost)); // 255
    println!("wrapping:   {}", battery.wrapping_add(boost)); // 4
    println!("plain +:    {}", battery + boost); // panics in debug builds
}
  • Debug builds panic on overflow. Release builds wrap around silently. Neither is what you meant.
  • checked_ gives an Option, saturating_ stops at the edge, wrapping_ goes round on purpose.
The final project's battery uses a check before subtracting, which is the same idea as saturating_sub. Students who write battery - 1 without a check get a panic in debug and u32::MAX battery in release, which is a fun bug to find in a review.

WebAssembly

Rust in the browser

rustup target add wasm32-unknown-unknown
cargo install wasm-pack
wasm-pack build --target web     # writes pkg/: a .wasm file and the JavaScript to load it
use wasm_bindgen::prelude::*;

#[wasm_bindgen]
pub fn run_mission_json(mission: &str) -> String {
    match robbie_mc::Mission::from_json(mission).and_then(|m| robbie_mc::run_mission(&m)) {
        Ok(report) => report.to_json(),
        Err(e) => format!("{{\"error\": \"{e}\"}}"),
    }
}

The same library runs in the terminal and in a web page. The course site's Robbie Arena runs missions in the browser, and the final project's stretch goal is to power it with yours.

WebAssembly is a small, fast instruction set every browser runs. Rust compiles to it with no garbage collector to ship, so the files are small. Not run in class: wasm-pack needs a download. Show the Arena page instead and say: that, but with your own Rust doing the work.

Publishing

From folder to crates.io

[package]
name = "ship_it"
version = "0.1.0"
edition = "2024"
description = "Robbie gets ready to ship"
license = "MIT"
repository = "https://github.com/you/ship_it"
keywords = ["robot", "teaching"]
/// Robbie's battery after a number of steps. Never goes below zero.
///
/// ```
/// assert_eq!(battery_after(20, 5), 15);
/// assert_eq!(battery_after(3, 10), 0);
/// ```
pub fn battery_after(start: u32, steps: u32) -> u32 {
    start.saturating_sub(steps)
}

fn main() {
    println!("{}", battery_after(20, 5));
}
cargo doc --open           # your docs as a website
cargo test --doc           # every ``` example in your docs is a test
cargo publish --dry-run    # pack and check, upload nothing
Doc examples are tests: if the docs go out of date, cargo test fails. That's why Rust crate docs are so reliable. Versions follow semver: 0.1.1 for fixes, 0.2.0 for breaking changes before 1.0. Publishing is permanent: you can yank a version but never delete it. Nobody publishes in class.
