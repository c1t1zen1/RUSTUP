1. Macros

You've used macros since your first program: println!, vec!, assert_eq!. The ! marks them. A macro runs while your program compiles and writes code in its place. macro_rules! makes a declarative macro: a list of arms, like a match, except it matches the shape of the code you pass in.

// A macro matches the shape of what you pass it, then writes code.
macro_rules! squeak {
    () => {
        println!("squeak")
    };
    ($times:expr) => {
        for _ in 0..$times {
            println!("squeak")
        }
    };
}

fn main() {
    squeak!(); // matches the first arm
    squeak!(2); // matches the second, with $times = 2
}

Inside a pattern, $name:kind captures a piece of code. The kinds you'll use most:

KindMatchesExample
exprAny expression3, a + b, name.len()
identA namebattery, Robbie
tyA typeu32, Vec<String>
literalA literal value"beep", 42
ttAny single token treeAlmost anything

Repetition is what makes macros worth having. $( ... ),* matches zero or more comma-separated items, and the same syntax in the arm's body repeats code once for each. Use + for one or more, and ? for zero or one.

// $( ... ),* matches a comma-separated list, and repeats the code for each.
macro_rules! parts_list {
    ($($part:expr),* $(,)?) => {
        vec![$(String::from($part)),*]
    };
}

fn main() {
    let spares = parts_list!["bolt", "spring", "left elbow"];
    println!("{spares:?}");
    let none: Vec<String> = parts_list![];
    println!("{} spares in the empty box", none.len());
}

A macro can call itself, peeling off one item each time. This one turns loudest!(a, b, c) into max(a, max(b, c)):

// A macro can call itself, peeling one item off each time.
macro_rules! loudest {
    ($x:expr) => { $x };
    ($x:expr, $($rest:expr),+) => {
        std::cmp::max($x, loudest!($($rest),+))
    };
}

fn main() {
    println!("loudest squeak: {}", loudest!(42, 87, 63, 12));
}

When no arm fits, nothing gets written, and you get "no rules expected this token":

Fails on purpose (no arm matches). Press Run and read the error.

macro_rules! squeak {
    () => {
        println!("squeak")
    };
}

fn main() {
    squeak!(3); // no arm takes an argument
}
Remember this

A macro is a match on code. And reach for it last: try a function, then a generic function, and only then a macro.

2. unsafe

Rust's guarantees come from checks the compiler can do. A few things it can't check, so they're locked behind an unsafe block. Inside one you may:

  1. Follow (dereference) a raw pointer, *const T or *mut T.
  2. Call an unsafe fn, which includes most functions from C.
  3. Read or write a static mut.
  4. Implement an unsafe trait such as Send by hand.
  5. Read a field of a union.

That's all. The borrow checker and type checker still run inside unsafe. Making a raw pointer is safe; following it isn't:

Fails on purpose (E0133). Press Run and read the error.

fn main() {
    let battery = 87;
    let p = &battery as *const i32; // making a raw pointer is safe
    println!("{}", *p); // reading through it is not
}
fn main() {
    let mut battery = 87;
    let p = &mut battery as *mut i32;
    // SAFETY: p came from a live, unique &mut just above, and nothing else
    // touches battery while we use it.
    unsafe {
        *p -= 10;
        println!("battery through a raw pointer: {}", *p);
    }
    println!("battery: {battery}");
}
Gotcha

If an unsafe promise is wrong, the result is undefined behaviour. The program might crash, might print nonsense, or might work perfectly until the day it matters. There's no error message. That's why every unsafe block needs a written argument.

Remember this

If you can't write the SAFETY comment, you can't write the block. Start every unsafe block with // SAFETY: and say why each rule holds here.

3. Safe wrappers

The skill isn't writing unsafe code. It's writing a safe function with a little unsafe inside, so nobody who calls it has to think about it. Here's a real reason to need one. The two halves of an array can't overlap, but the borrow checker sees two &mut borrows of one thing:

Fails on purpose (E0499). Press Run and read the error.

fn main() {
    let mut joints = [5, 9, 2, 7];
    let left = &mut joints[..2];
    let right = &mut joints[2..]; // the halves don't overlap, but Rust can't tell
    left[0] = 0;
    right[0] = 0;
    println!("{joints:?}");
}

The standard library already wraps this for you:

fn main() {
    let mut joints = [5, 9, 2, 7];
    let (left, right) = joints.split_at_mut(2); // std did the unsafe part for you
    left[0] = 0;
    right[0] = 0;
    println!("{joints:?}");
}

And here's roughly how it's built. The signature promises both halves live no longer than items, so every caller is still fully checked:

/// Two halves you can change at once. Safe to call, unsafe inside.
fn split_halves(items: &mut [u32]) -> (&mut [u32], &mut [u32]) {
    let len = items.len();
    let mid = len / 2;
    let ptr = items.as_mut_ptr();
    // SAFETY: ptr is valid for len items. 0..mid and mid..len never overlap,
    // and both slices live no longer than the borrow of items.
    unsafe {
        (
            std::slice::from_raw_parts_mut(ptr, mid),
            std::slice::from_raw_parts_mut(ptr.add(mid), len - mid),
        )
    }
}

fn main() {
    let mut joints = [5, 9, 2, 7, 4];
    let (left, right) = split_halves(&mut joints);
    left[0] = 0;
    right[0] = 0;
    println!("{joints:?}");
}
Remember this

Unsafe on the inside, safe on the outside. Vec, String and split_at_mut are all built this way. Look for the safe standard function before you write your own.

4. FFI with C

FFI, the foreign function interface, lets Rust call code written in C, and lets C (or Python, Swift, anything that speaks C) call Rust. You declare C functions in an unsafe extern "C" block. Since Rust 2024 the block itself says unsafe, because you're promising the declarations match the real functions.

use std::ffi::{CStr, c_char};

// Rust 2024: an extern block is unsafe, because Rust can't check what's in C.
unsafe extern "C" {
    safe fn abs(x: i32) -> i32; // `safe`: you promise it's fine with any i32... almost
    fn strlen(s: *const c_char) -> usize; // a raw pointer, so calling it stays unsafe
}

fn c_strlen(s: &CStr) -> usize {
    // SAFETY: a &CStr always ends in a 0 byte, which is what strlen needs.
    unsafe { strlen(s.as_ptr()) }
}

fn main() {
    println!("C says |-12| = {}", abs(-12));
    println!("C says \"robbie\" has {} bytes", c_strlen(c"robbie"));
}

A function marked safe fn can be called normally. Everything else in the block is unsafe to call:

Fails on purpose (E0133). Press Run and read the error.

unsafe extern "C" {
    fn abs(x: i32) -> i32;
}

fn main() {
    println!("{}", abs(-12)); // not marked safe, so the call needs unsafe
}

C strings are bytes ending in a 0 byte. Rust's String knows its length instead, so there are separate types for C strings:

use std::ffi::{CStr, CString};

fn main() {
    // Rust strings know their length. C strings end at a 0 byte instead.
    let name = CString::new("Robbie v11").unwrap();
    println!("{} bytes, plus the 0 at the end", name.as_bytes().len());

    let literal: &CStr = c"squeak"; // a C string literal, checked at compile time
    println!("{literal:?} back in Rust: {}", literal.to_str().unwrap());

    // A 0 byte in the middle can't be a C string.
    println!("{:?}", CString::new("rob\0bie").is_err());
}

i32, u8, f64, usizeint, unsigned char, double, size_t

Going the other way, extern "C" on a Rust function plus #[unsafe(no_mangle)] makes it callable from C:

// Going the other way: a Rust function that C (or Python, or Swift) can call.
#[unsafe(no_mangle)]
pub extern "C" fn robbie_battery_after(start: u32, steps: u32) -> u32 {
    start.saturating_sub(steps)
}

fn main() {
    // You can still call it from Rust like any function.
    println!("battery after 30 steps: {}", robbie_battery_after(20, 30));
}
Gotcha

The C library has its own rules, and Rust can't check them. C's abs(INT_MIN) is undefined behaviour, so a safe wrapper must never pass it i32::MIN. That's Lab 6, step 3.

5. Speed and overflow

Rust is fast, but only in release mode. A debug build skips optimization and adds checks, so it can be ten to fifty times slower. Never time a debug build.

cargo build --release            # target/release/, optimized
cargo run --release --example bench

To time something, run it several times and keep the best run, which is the one least disturbed by the rest of the computer. std::hint::black_box stops the optimizer from deleting work whose answer nobody uses:

use std::hint::black_box;
use std::time::Instant;

fn vowels(text: &str) -> usize {
    text.bytes()
        .filter(|b| matches!(b.to_ascii_lowercase(), b'a' | b'e' | b'i' | b'o' | b'u'))
        .count()
}

fn main() {
    let text = "Robbie oils his elbows again. ".repeat(10_000);
    let mut best = u128::MAX;
    for _ in 0..10 {
        let start = Instant::now();
        black_box(vowels(black_box(&text))); // stop the optimizer skipping the work
        best = best.min(start.elapsed().as_micros());
    }
    println!(
        "{} vowels, best of 10 runs: {best} microseconds",
        vowels(&text)
    );
}

Numbers have edges. A debug build panics when arithmetic overflows; a release build quietly wraps around. Say what you want instead:

Compiles, then panics on purpose. Press Run and read the message.

fn main() {
    let battery: u8 = 250;
    let boost: u8 = std::hint::black_box(10);
    println!("checked:    {:?}", battery.checked_add(boost)); // None
    println!("saturating: {}", battery.saturating_add(boost)); // 255
    println!("wrapping:   {}", battery.wrapping_add(boost)); // 4
    println!("plain +:    {}", battery + boost); // panics in debug builds
}
Remember this

checked_ asks, saturating_ stops, wrapping_ loops. checked_add gives None at the edge, saturating_add stays at the limit, wrapping_add goes round on purpose.

6. WebAssembly

WebAssembly (wasm) is a compact instruction set that every browser can run at near-native speed. Rust compiles to it directly, and with no garbage collector to ship, the files are small. wasm-bindgen writes the glue between Rust and JavaScript, and wasm-pack runs the whole build:

rustup target add wasm32-unknown-unknown
cargo install wasm-pack
wasm-pack build --target web
[lib]
crate-type = ["cdylib", "rlib"]

[dependencies]
wasm-bindgen = "0.2"
use wasm_bindgen::prelude::*;

#[wasm_bindgen]
pub fn run_mission_json(mission: &str) -> String {
    match robbie_mc::Mission::from_json(mission).and_then(|m| robbie_mc::run_mission(&m)) {
        Ok(report) => report.to_json(),
        Err(e) => format!("{{\"error\": \"{e}\"}}"),
    }
}

Threads don't exist in a plain browser build, so a wasm build uses run_mission, not run_fleet. Try the course's Robbie Arena to see missions run in the browser.

7. Docs and publishing

A /// comment documents the item below it, and //! documents the whole module or crate. Code inside ``` in a doc comment is a real test: cargo test runs it, so your docs can't go out of date.

/// Robbie's battery after a number of steps. Never goes below zero.
///
/// ```
/// assert_eq!(battery_after(20, 5), 15);
/// assert_eq!(battery_after(3, 10), 0);
/// ```
pub fn battery_after(start: u32, steps: u32) -> u32 {
    start.saturating_sub(steps)
}

fn main() {
    println!("{}", battery_after(20, 5));
}

To publish to crates.io, the [package] section needs a description and a license, and should have a repository and keywords:

[package]
name = "ship_it"
version = "0.1.0"
edition = "2024"
description = "Robbie gets ready to ship"
license = "MIT"
repository = "https://github.com/you/ship_it"
keywords = ["robot", "teaching"]
cargo doc --open            # your docs, as a website
cargo test --doc            # run just the doc examples
cargo publish --dry-run     # pack and check everything, upload nothing
cargo publish               # for real, and forever
Gotcha

Publishing is permanent. You can yank a version so new projects don't pick it up, but you can never delete it. Version numbers follow semver: 0.1.1 for a fix, 0.2.0 for a breaking change (until 1.0).

8. Code review

Fifteen of the final project's points are a code review. The grader flags lines worth a look, and a person decides. What reviewers look for:

  • Errors, not crashes. unwrap, expect and indexing that can go out of bounds don't belong in library code. Return a Result.
  • Ownership that fits. .clone() on every line usually means the design is fighting the borrow checker. Borrow where you can.
  • Structure. Small functions, one job each, one match per enum rather than the same check copied in five places.
  • Names. parts_left, not n. start, not tmp.
  • unsafe with a SAFETY comment, or no unsafe at all.

Run the grader, then drop its grade.json on the Review Lab page to see every flag with a plain-English explanation.

Remember this

A good review comment says what, where and why. "world.rs:40 unwraps the first row, which panics on an empty map" helps. "Bad code" doesn't.

Practice questions

1. Why is println! a macro and not a function?

It takes any number of arguments, and checks the format string against them while compiling. A Rust function can't do either.

2. In a macro pattern, what does $($x:expr),* match?

Zero or more expressions separated by commas, each captured as $x.

3. Does unsafe turn off the borrow checker?

No. It only unlocks five extra abilities, like following a raw pointer and calling unsafe functions. Every other check still runs.

4. Making a raw pointer is safe. Why is following one unsafe?

The compiler can't prove the pointer still points at a live value of the right type, so you have to promise it.

5. What should every unsafe block have above it?

A // SAFETY: comment explaining why every rule the unsafe operation needs holds at that spot.

6. You need two &mut halves of one slice. What do you reach for first?

split_at_mut, the safe standard function. Only write raw-pointer code if no safe function does the job.

7. Why is abs from C not completely safe to call with any i32?

C's abs(INT_MIN) is undefined behaviour, because the positive answer doesn't fit. A safe wrapper must rule that input out.

8. Why time code with --release?

Debug builds aren't optimized and include extra checks, so their timings don't tell you how fast the real program is.

9. What do 250u8.checked_add(10) and 250u8.saturating_add(10) give?

None and 255.

10. Why do the examples in your doc comments matter for publishing?

cargo test runs them, so the documentation is checked every time and can't quietly go out of date.
