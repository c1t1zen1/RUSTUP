1. Vec

A Vec<T> is a list that can grow. All its items have the same type, sit next to each other in memory, and are numbered from 0.

fn main() {
    // vec! builds a Vec with items already in it
    let mut parts = vec![String::from("left knee"), String::from("right elbow")];
    parts.push(String::from("antenna")); // push adds one to the end

    println!("{} rusty parts", parts.len());
    println!("first: {}", parts[0]);

    // get() returns an Option, so a bad index can't crash you
    match parts.get(10) {
        Some(p) => println!("found {p}"),
        None => println!("no part number 10"),
    }

    for p in &parts {
        println!("- {p}");
    }
}

Indexing with parts[i] panics if i is past the end. parts.get(i) returns an Option, so you decide what happens. A few more everyday methods:

fn main() {
    let mut queue = vec![3, 1, 4, 1, 5, 9, 2, 6];
    queue.sort();
    queue.dedup(); // removes repeats that sit next to each other
    println!("{queue:?}");
    println!("contains 4? {}", queue.contains(&4));
    println!("last: {:?}", queue.last());
    queue.retain(|&n| n % 2 == 1); // keep only the odd ones
    println!("odd: {queue:?}");
    let popped = queue.pop();
    println!("popped {popped:?}, left {queue:?}");
}

Why you can't push while borrowing

When a Vec is full, push moves every item to a bigger block of memory. Any reference into the old block would be left pointing at nothing, so Rust won't let you change a Vec while a reference into it is still in use:

Fails on purpose (E0502). Press Run and read the error.

fn main() {
    let mut readings = vec![87, 42, 99];
    let first = &readings[0]; // a shared borrow into the Vec
    readings.push(13); // push may move the whole Vec to new memory
    println!("first reading: {first}");
}
Remember this

Don't hold a page number while someone rebinds the book. Copy the value out, or finish with the reference before you push.

2. HashMap

A HashMap<K, V> stores values under keys, so you can look them up by name instead of by position. It's not in the prelude, so start with use std::collections::HashMap;.

use std::collections::HashMap;

fn main() {
    let mut rust_level: HashMap<String, u8> = HashMap::new();
    rust_level.insert(String::from("knees"), 60);
    rust_level.insert(String::from("antenna"), 15);
    rust_level.insert(String::from("knees"), 65); // same key: replaces 60

    println!("knees: {:?}", rust_level.get("knees"));
    println!("toes: {:?}", rust_level.get("toes"));

    if let Some(level) = rust_level.get_mut("antenna") {
        *level += 5;
    }

    let mut parts: Vec<_> = rust_level.iter().collect();
    parts.sort(); // a HashMap has no order, so sort before printing
    println!("{parts:?}");
}
Gotcha

A HashMap has no order, and the order changes from run to run. Sort the pairs before printing or comparing them, or use a BTreeMap, which keeps its keys sorted.

The entry API

The most useful HashMap pattern: find the slot for a key, fill it with a starting value if it's empty, then update it.

use std::collections::HashMap;

fn main() {
    let log = "squeak clunk squeak beep squeak clunk";
    let mut counts: HashMap<&str, u32> = HashMap::new();
    for sound in log.split_whitespace() {
        // find the slot for this key, make it 0 if it's new, then add 1
        *counts.entry(sound).or_insert(0) += 1;
    }
    let mut sorted: Vec<_> = counts.into_iter().collect();
    sorted.sort_by(|a, b| b.1.cmp(&a.1).then(a.0.cmp(b.0)));
    println!("{sorted:?}");
}
Remember this

Entry, or insert, then bump: *map.entry(key).or_insert(0) += 1. For a list per key, map.entry(key).or_insert_with(Vec::new).push(item).

3. Traits

A trait is a named set of methods. A type implements the trait by providing those methods, and from then on any code that needs "something with these methods" can use it.

trait Speak {
    fn speak(&self) -> String;
}

struct Robot {
    name: String,
}

struct Toaster;

impl Speak for Robot {
    fn speak(&self) -> String {
        format!("Hello, I am {}.", self.name)
    }
}

impl Speak for Toaster {
    fn speak(&self) -> String {
        String::from("Ding!")
    }
}

fn main() {
    let robbie = Robot {
        name: String::from("Robbie"),
    };
    println!("{}", robbie.speak());
    println!("{}", Toaster.speak());
}

Rust has no inheritance. Where Java would use a base class and Python a shared parent, Rust uses a trait, and shares code with default methods:

trait Speak {
    fn name(&self) -> String;

    // a default method: every implementor gets it for free
    fn greet(&self) -> String {
        format!("Hi, I'm {}!", self.name())
    }
}

struct Robot;
struct Parrot;

impl Speak for Robot {
    fn name(&self) -> String {
        String::from("Robbie")
    }
}

impl Speak for Parrot {
    fn name(&self) -> String {
        String::from("Polly")
    }
    // ...or it can bring its own
    fn greet(&self) -> String {
        String::from("Polly wants a cracker!")
    }
}

fn main() {
    println!("{}", Robot.greet());
    println!("{}", Parrot.greet());
}

A type that implements a trait must provide every method without a default, or the compiler names the missing one:

Fails on purpose (E0046). Press Run and read the error.

trait Bot {
    fn name(&self) -> String;
    fn power(&self) -> u32;
}

struct Drone;

impl Bot for Drone {
    fn name(&self) -> String {
        String::from("Zippy")
    }
    // power() is missing
}

fn main() {
    println!("{}", Drone.name());
}

Traits as parameters

A function can accept any type that implements a trait. The short form is impl Trait; the long form is a generic with a bound. They mean the same thing.

trait Speak {
    fn speak(&self) -> String;
}

struct Robot;
impl Speak for Robot {
    fn speak(&self) -> String {
        String::from("beep boop")
    }
}

// "anything that can speak", the short way
fn announce(thing: &impl Speak) {
    println!("Announcing: {}", thing.speak());
}

// the same thing, the long way, with a generic and a trait bound
fn announce_twice<T: Speak>(thing: &T) {
    println!("{0} {0}", thing.speak());
}

fn main() {
    announce(&Robot);
    announce_twice(&Robot);
}
Remember this

A trait is a job description. Any type that can do the job can apply, even a toaster.

4. derive and the standard traits

Most of the operators and helpers you use are traits from the standard library. #[derive(...)] asks the compiler to write the obvious version for you:

#[derive(Debug, Clone, Copy, PartialEq, PartialOrd)]
struct Battery(u8);

#[derive(Debug, Clone, PartialEq, Eq, Hash, PartialOrd, Ord)]
enum Rust {
    None,
    Spotty,
    Streaky,
    Flaky,
}

fn main() {
    let a = Battery(87);
    let b = a; // Copy: a is still usable
    println!("{a:?} == {b:?}? {}", a == b);
    println!("{:?} < {:?}? {}", Battery(20), a, Battery(20) < a);
    // derived Ord on an enum follows the order the variants are written in
    println!("Flaky worse than Spotty? {}", Rust::Flaky > Rust::Spotty);
    println!("{:?}", [Rust::Streaky, Rust::None].iter().max());
}

use std::fmt;

struct Robot {
    name: String,
    rust: u8,
}

impl fmt::Display for Robot {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "{} ({}% rust)", self.name, self.rust)
    }
}

fn main() {
    let robbie = Robot {
        name: String::from("Robbie"),
        rust: 50,
    };
    println!("{robbie}"); // uses Display
    let label = robbie.to_string(); // Display gives you to_string for free
    println!("{} characters", label.len());
}
Gotcha

f64 is PartialOrd but not Ord, because NaN isn't less than, equal to or greater than anything. So vec_of_f64.sort() doesn't compile. Use sort_by(|a, b| a.total_cmp(b)).

5. Generics

A generic function works for many types. You name a type parameter in angle brackets, and use bounds to say what the type must be able to do.

fn largest<T: PartialOrd + Copy>(items: &[T]) -> T {
    let mut best = items[0];
    for &item in items {
        if item > best {
            best = item;
        }
    }
    best
}

fn main() {
    println!("{}", largest(&[87, 42, 99, 13]));
    println!("{}", largest(&[0.5, 2.25, 1.0]));
    println!("{}", largest(&['r', 'u', 's', 't']));
}

The body can only use what the bounds promise. Comparing two values of an unbounded T fails, because some types can't be compared:

Fails on purpose (E0369). Press Run and read the error.

fn largest<T>(items: &[T]) -> &T {
    let mut best = &items[0];
    for item in items {
        if item > best {
            best = item;
        }
    }
    best
}

fn main() {
    println!("{}", largest(&[87, 42, 99]));
}

Structs and enums can be generic too. You've been using them since Session 1: Vec<T>, Option<T>, Result<T, E>.

#[derive(Debug)]
struct Pair<T> {
    left: T,
    right: T,
}

impl<T: PartialOrd> Pair<T> {
    fn bigger(&self) -> &T {
        if self.left >= self.right {
            &self.left
        } else {
            &self.right
        }
    }
}

fn main() {
    let arms = Pair {
        left: 40,
        right: 72,
    };
    let names = Pair {
        left: "Robbie",
        right: "Zippy",
    };
    println!("{arms:?} -> {}", arms.bigger());
    println!("{names:?} -> {}", names.bigger());
}

When bounds get long, move them into a where clause:

use std::fmt::Display;

// a where clause moves long bounds out of the way
fn report<T, U>(name: T, value: U) -> String
where
    T: Display,
    U: Display + PartialOrd + From<u8>,
{
    let warning = if value > U::from(50) { " (!)" } else { "" };
    format!("{name}: {value}{warning}")
}

fn main() {
    println!("{}", report("knee rust", 72));
    println!("{}", report("antenna rust", 15.5));
}

Generics cost nothing at runtime. The compiler writes a separate copy of the function for each type you use it with, which is called monomorphization.

Remember this

Generics are a stencil, bounds are the fine print.

6. Trait objects

A Vec holds one type. To keep a robot, a drone and a vacuum in the same list, store each one in a Box behind the trait: Box<dyn Trait>.

trait Speak {
    fn speak(&self) -> String;
}

struct Robot;
struct Drone;
struct Vacuum;

impl Speak for Robot {
    fn speak(&self) -> String {
        "beep".into()
    }
}
impl Speak for Drone {
    fn speak(&self) -> String {
        "bzzzz".into()
    }
}
impl Speak for Vacuum {
    fn speak(&self) -> String {
        "vrrrm".into()
    }
}

fn main() {
    // one Vec, three different types: each lives in a Box behind the trait
    let studio: Vec<Box<dyn Speak>> = vec![Box::new(Robot), Box::new(Drone), Box::new(Vacuum)];
    for thing in &studio {
        println!("{}", thing.speak());
    }
}

7. Closures

A closure is a small function without a name, written |arguments| body. It can use variables from the place it was written.

fn main() {
    let double = |n: u32| n * 2;
    println!("{}", double(21));

    // a closure can use variables from where it was written
    let limit = 50;
    let too_rusty = |rust: u8| rust > limit;
    println!("{} {}", too_rusty(32), too_rusty(72));

    // closures are how you customise library functions
    let mut parts = vec!["knee", "antenna", "elbow"];
    parts.sort_by_key(|p| p.len());
    println!("{parts:?}");
}

What a closure does with the variables it captures decides which of three traits it implements:

fn main() {
    let mut squeaks = 0;
    // this closure changes squeaks, so it has to be mut itself
    let mut walk = |steps: u32| {
        squeaks += steps / 2;
    };
    walk(4);
    walk(6);
    println!("{squeaks} squeaks so far");
}
TraitCaptured variables areCan be called
Fnonly readany number of times
FnMutchangedany number of times, if the closure is mut
FnOncemoved out and used uponce

move in front of a closure makes it own what it captures. That's how a function can build a closure and hand it back:

// returns "some closure that takes a u32 and gives a u32"
fn make_charger(percent: u32) -> impl Fn(u32) -> u32 {
    move |battery| (battery + percent).min(100)
}

fn main() {
    let quick = make_charger(10);
    let full = make_charger(100);
    println!("{} {} {}", quick(50), quick(95), full(3));
}
Remember this

Fn looks, FnMut touches, FnOnce takes: the same three-way split as &self, &mut self and self.

8. Iterators

An iterator produces items one at a time. You build a pipeline of adapters (which transform the stream) and finish with a consumer (which runs it and produces a result).

fn main() {
    let readings = [87, 12, 99, 45, 3, 76];

    let low: Vec<i32> = readings.iter().filter(|&&r| r < 50).copied().collect();
    let total: i32 = readings.iter().sum();
    let doubled: Vec<i32> = readings.iter().map(|r| r * 2).collect();
    let any_critical = readings.iter().any(|&r| r < 5);

    println!("low: {low:?}");
    println!("total: {total}, average: {}", total / readings.len() as i32);
    println!("doubled: {doubled:?}");
    println!("any critical? {any_critical}");
}

Iterators are lazy: building the pipeline does nothing. Work happens only when a consumer asks for items, and only for as many as it asks for.

fn main() {
    let parts = ["knee", "elbow", "antenna", "visor", "toe"];
    // nothing happens until something asks for items
    let checked = parts.iter().map(|p| {
        println!("  checking {p}");
        p.len()
    });
    println!("built the iterator, nothing checked yet");
    let first_two: Vec<usize> = checked.take(2).collect();
    println!("lengths: {first_two:?}");
}
fn main() {
    let parts = ["knee", "elbow", "antenna"];
    let rust = [60, 35, 15];

    for (i, p) in parts.iter().enumerate() {
        println!("{}. {p}", i + 1);
    }
    let pairs: Vec<(&str, i32)> = parts.iter().copied().zip(rust).collect();
    println!("{pairs:?}");

    let worst = pairs.iter().max_by_key(|(_, r)| *r);
    println!("worst: {worst:?}");

    let sentence = parts
        .iter()
        .rev()
        .fold(String::new(), |acc, p| acc + p + " ");
    println!("backwards: {}", sentence.trim_end());

    let countdown: Vec<u32> = (1..=10).rev().step_by(3).collect();
    println!("{countdown:?}");
}

Most loops that build a result can become a chain, and the chain usually says what it means more plainly:

fn main() {
    let tasks = [("oil knees", 20), ("dust wall", 30), ("find umbrella", 10)];

    // the loop way
    let mut total = 0;
    for (_, minutes) in &tasks {
        if *minutes >= 15 {
            total += minutes;
        }
    }

    // the iterator way: same answer, says what it means
    let total2: i32 = tasks.iter().map(|(_, m)| m).filter(|&&m| m >= 15).sum();

    println!("{total} == {total2}");
}
StartGives you
.iter()&T: borrows each item
.iter_mut()&mut T: change items in place
.into_iter()T: takes the items, using up the collection
Remember this

Iterators are a conveyor belt. filter is the inspector, map is the paint shop, collect is the box at the end. Nothing moves until someone switches the belt on.

9. Lifetimes in depth

Every reference has a lifetime: the stretch of code where it's valid. Usually the compiler works it out. When a function returns a reference and takes two, it can't tell which one the answer borrows from:

Fails on purpose (E0106). Press Run and read the error.

fn longer(a: &str, b: &str) -> &str {
    if a.len() >= b.len() { a } else { b }
}

fn main() {
    println!("{}", longer("knee", "antenna"));
}

You answer with a lifetime parameter. 'a is a name, like T, but for "how long this borrow lasts":

// 'a says: the answer lives no longer than the shorter-lived of a and b
fn longer<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

fn main() {
    let part = String::from("antenna");
    let answer = longer("knee", &part);
    println!("{answer}");
}

The annotation is a promise the compiler checks at every call. Here it catches an answer that would outlive one of its sources:

Fails on purpose (E0597). Press Run and read the error.

fn longer<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

fn main() {
    let answer;
    let knee = String::from("knee");
    {
        let antenna = String::from("antenna");
        answer = longer(&knee, &antenna);
    } // antenna is dropped here...
    println!("{answer}"); // ...but answer might point into it
}

Only tie the output to the inputs it really borrows from. In the lab, next_in_room returns a task from tasks, never from room, so only tasks gets 'a:

pub fn next_in_room<'a>(tasks: &'a [Task], room: &str) -> Option<&'a Task>

A struct that holds a reference needs a lifetime parameter too, and can't outlive what it borrows:

// a struct that borrows text instead of owning it
struct Excerpt<'a> {
    line: &'a str,
}

impl<'a> Excerpt<'a> {
    fn first_word(&self) -> &'a str {
        self.line.split_whitespace().next().unwrap_or("")
    }
}

fn main() {
    let log = String::from("SQUEAK detected in left knee. Again.");
    let first_line = Excerpt {
        line: log.split('.').next().unwrap_or(""),
    };
    println!("{} / {}", first_line.line, first_line.first_word());
}

When you don't have to write them

  • One reference in, a reference out: the output borrows from that input.
  • A method with &self: the output borrows from self.
  • Anywhere else, if the compiler asks, it's asking a real question: "which input?".
Remember this

A lifetime is a label on a borrowed tool: "return to the owner before they leave". It never makes anything live longer.

Practice questions

1. What's the difference between v[5] and v.get(5)?

v[5] panics if there's no item 5. v.get(5) returns None instead.

2. Why does pushing to a Vec while holding &v[0] fail?

Pushing may move the items to new memory, which would leave the reference dangling. The borrow checker sees the shared borrow still in use and refuses the mutable one (E0502).

3. Write the line that counts words into counts: HashMap<&str, u32>.

*counts.entry(word).or_insert(0) += 1;

4. A trait has two methods, one with a default. How many must an impl write?

One: the method without a default. It may also override the default.

5. What's the difference between fn f(x: &impl Speak) and fn f<T: Speak>(x: &T)?

Nothing that matters here. Both accept any type that implements Speak, decided at compile time.

6. Why won't fn biggest<T>(a: T, b: T) -> T { if a > b { a } else { b } } compile?

T has no bound, so the compiler can't assume it supports >. Add T: PartialOrd.

7. When do you need Box<dyn Trait> instead of a generic?

When you need values of different types together, like one Vec of robots, drones and vacuums.

8. A closure adds to a counter it captured. Which trait does it implement, and what must its binding be?

FnMut, and it must be declared let mut.

9. What does (1..=4).map(|n| n * n).sum::<u32>() give?

1 + 4 + 9 + 16 = 30.

10. Why does next_in_room put 'a on tasks but not on room?

The answer only ever borrows from tasks. Tying it to room too would wrongly stop callers dropping the room name early.
