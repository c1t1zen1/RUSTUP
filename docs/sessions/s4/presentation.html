Vec

A list that grows

fn main() {
    // vec! builds a Vec with items already in it
    let mut parts = vec![String::from("left knee"), String::from("right elbow")];
    parts.push(String::from("antenna")); // push adds one to the end

    println!("{} rusty parts", parts.len());
    println!("first: {}", parts[0]);

    // get() returns an Option, so a bad index can't crash you
    match parts.get(10) {
        Some(p) => println!("found {p}"),
        None => println!("no part number 10"),
    }

    for p in &parts {
        println!("- {p}");
    }
}
  • vec![...] makes one with items, push adds to the end.
  • parts[0] panics on a bad index. parts.get(10) gives an Option instead.
  • Loop over &parts to borrow; looping over parts moves the whole Vec.
A Vec is three numbers on the stack (pointer, length, capacity) and the items on the heap. That picture explains the next slide. Ask: what's the difference between for p in parts and for p in &parts? (The first consumes the Vec; Session 2 callback.)

Vec and the borrow checker

Why you can't push while you're looking

Fails on purpose (E0502). Press Run and read the error.

fn main() {
    let mut readings = vec![87, 42, 99];
    let first = &readings[0]; // a shared borrow into the Vec
    readings.push(13); // push may move the whole Vec to new memory
    println!("first reading: {first}");
}

When a Vec runs out of room, push moves every item to a bigger block of memory. A reference into the old block would point at nothing. Rust sees the shared borrow first still in use and refuses the &mut that push needs (E0502).

Remember this

Don't hold a page number while someone rebinds the book. Read the value out first (let first = readings[0]; copies it), or push before you borrow.

This is the classic "iterator invalidation" bug from C++, caught at compile time. Fix it live two ways: copy the value out (i32 is Copy), or move the println above the push so the borrow ends first.

HashMap

Look things up by name

use std::collections::HashMap;

fn main() {
    let mut rust_level: HashMap<String, u8> = HashMap::new();
    rust_level.insert(String::from("knees"), 60);
    rust_level.insert(String::from("antenna"), 15);
    rust_level.insert(String::from("knees"), 65); // same key: replaces 60

    println!("knees: {:?}", rust_level.get("knees"));
    println!("toes: {:?}", rust_level.get("toes"));

    if let Some(level) = rust_level.get_mut("antenna") {
        *level += 5;
    }

    let mut parts: Vec<_> = rust_level.iter().collect();
    parts.sort(); // a HashMap has no order, so sort before printing
    println!("{parts:?}");
}
  • insert adds or replaces. get gives an Option<&V>.
  • A HashMap has no order. Sort the pairs before you print or test them.
  • Need order? BTreeMap keeps keys sorted, with the same methods.
HashMap isn't in the prelude, so it needs a use line. The iteration order is deliberately randomised per run (a defence against hash-flooding attacks). Students who print a HashMap in a test will see it pass and then fail; tell them now.

The entry API

Count anything in one line

use std::collections::HashMap;

fn main() {
    let log = "squeak clunk squeak beep squeak clunk";
    let mut counts: HashMap<&str, u32> = HashMap::new();
    for sound in log.split_whitespace() {
        // find the slot for this key, make it 0 if it's new, then add 1
        *counts.entry(sound).or_insert(0) += 1;
    }
    let mut sorted: Vec<_> = counts.into_iter().collect();
    sorted.sort_by(|a, b| b.1.cmp(&a.1).then(a.0.cmp(b.0)));
    println!("{sorted:?}");
}

entry(key) finds the slot for a key. .or_insert(0) fills it with 0 if it's new and hands you a &mut to the value either way. *... += 1 bumps it.

Remember this

Entry, or insert, then bump. *map.entry(k).or_insert(0) += 1 is the tally-counter idiom. You'll use it in the lab and the homework.

Compare to the Python dict.get(k, 0) + 1 dance, which looks the key up twice. The entry API looks it up once. or_insert_with(Vec::new) is the version for building lists per key.

Traits

"Anything that can do this"

trait Speak {
    fn speak(&self) -> String;
}

struct Robot {
    name: String,
}

struct Toaster;

impl Speak for Robot {
    fn speak(&self) -> String {
        format!("Hello, I am {}.", self.name)
    }
}

impl Speak for Toaster {
    fn speak(&self) -> String {
        String::from("Ding!")
    }
}

fn main() {
    let robbie = Robot {
        name: String::from("Robbie"),
    };
    println!("{}", robbie.speak());
    println!("{}", Toaster.speak());
}

A trait names a behaviour: a list of methods a type promises to have. Any type can sign up with impl Trait for Type. A robot and a toaster have nothing in common except that both can speak, and that's enough.

For Java and C# folks: a trait is an interface. For Python folks: it's duck typing that the compiler checks. There's no inheritance in Rust; you build behaviour by implementing traits, and share code with default methods (next slide) and generics.

Default methods

Write it once, override when you need to

trait Speak {
    fn name(&self) -> String;

    // a default method: every implementor gets it for free
    fn greet(&self) -> String {
        format!("Hi, I'm {}!", self.name())
    }
}

struct Robot;
struct Parrot;

impl Speak for Robot {
    fn name(&self) -> String {
        String::from("Robbie")
    }
}

impl Speak for Parrot {
    fn name(&self) -> String {
        String::from("Polly")
    }
    // ...or it can bring its own
    fn greet(&self) -> String {
        String::from("Polly wants a cracker!")
    }
}

fn main() {
    println!("{}", Robot.greet());
    println!("{}", Parrot.greet());
}

A trait can provide a method body. Every type that implements the trait gets it for free, and any type can replace it with its own. The default can call the trait's other methods, even though it doesn't know which type it's running on.

The homework uses exactly this: Bot::label has a default, and Robbie overrides it to add "squeak" when he's 50% rust or more. Point out that greet calls self.name(), a method it hasn't seen implemented yet.

Keeping the promise

A trait is a contract, all of it

Fails on purpose (E0046). Press Run and read the error.

trait Bot {
    fn name(&self) -> String;
    fn power(&self) -> u32;
}

struct Drone;

impl Bot for Drone {
    fn name(&self) -> String {
        String::from("Zippy")
    }
    // power() is missing
}

fn main() {
    println!("{}", Drone.name());
}

Forget a required method and the compiler names it (E0046). Its help even offers the exact signature to paste in. Default methods are the only ones you can leave out.

Run it. Read the "missing power in implementation" error and copy the suggested signature in. Then ask: which methods could the trait have given defaults for, and why not power?

Traits as parameters

Functions that take "anything that can speak"

trait Speak {
    fn speak(&self) -> String;
}

struct Robot;
impl Speak for Robot {
    fn speak(&self) -> String {
        String::from("beep boop")
    }
}

// "anything that can speak", the short way
fn announce(thing: &impl Speak) {
    println!("Announcing: {}", thing.speak());
}

// the same thing, the long way, with a generic and a trait bound
fn announce_twice<T: Speak>(thing: &T) {
    println!("{0} {0}", thing.speak());
}

fn main() {
    announce(&Robot);
    announce_twice(&Robot);
}

&impl Speak is shorthand for a generic type T with the bound T: Speak. Both mean: I'll take any type, as long as it implements Speak. The compiler writes a separate copy for each type you actually use, so it's as fast as if you'd written them by hand.

That compile-time copying is called monomorphization. It's why Rust generics cost nothing at runtime. Use impl Trait for simple cases; the long form when two parameters must be the same type, or when bounds get long.

derive

Traits the compiler writes for you

#[derive(Debug, Clone, Copy, PartialEq, PartialOrd)]
struct Battery(u8);

#[derive(Debug, Clone, PartialEq, Eq, Hash, PartialOrd, Ord)]
enum Rust {
    None,
    Spotty,
    Streaky,
    Flaky,
}

fn main() {
    let a = Battery(87);
    let b = a; // Copy: a is still usable
    println!("{a:?} == {b:?}? {}", a == b);
    println!("{:?} < {:?}? {}", Battery(20), a, Battery(20) < a);
    // derived Ord on an enum follows the order the variants are written in
    println!("Flaky worse than Spotty? {}", Rust::Flaky > Rust::Spotty);
    println!("{:?}", [Rust::Streaky, Rust::None].iter().max());
}
deriveGives you
Debug{:?} printing
Clone / Copy.clone() / copy instead of move
PartialEq / Eq== and !=
PartialOrd / Ord<, >, sorting, max
HashUse it as a HashMap key
DefaultType::default()
derive works when every field already implements the trait. You can't derive Copy for a struct with a String in it. Derived Ord on an enum follows declaration order, which is a neat trick for severity levels.

Display

Teach your type to print itself

use std::fmt;

struct Robot {
    name: String,
    rust: u8,
}

impl fmt::Display for Robot {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "{} ({}% rust)", self.name, self.rust)
    }
}

fn main() {
    let robbie = Robot {
        name: String::from("Robbie"),
        rust: 50,
    };
    println!("{robbie}"); // uses Display
    let label = robbie.to_string(); // Display gives you to_string for free
    println!("{} characters", label.len());
}

Debug is for programmers and can be derived. Display is for people, so you write it yourself. Implement it once and you get {}, format! and .to_string() for free.

You did this in Homework 3 for the error types. That's the pattern: implement a standard trait, and the standard library lights up for your type. Same for Iterator, From, Default, Add and more.

Generics

One function, many types

fn largest<T: PartialOrd + Copy>(items: &[T]) -> T {
    let mut best = items[0];
    for &item in items {
        if item > best {
            best = item;
        }
    }
    best
}

fn main() {
    println!("{}", largest(&[87, 42, 99, 13]));
    println!("{}", largest(&[0.5, 2.25, 1.0]));
    println!("{}", largest(&['r', 'u', 's', 't']));
}

<T: PartialOrd + Copy> reads: "for any type T that can be compared and copied". Numbers, floats and chars all qualify, so one largest covers them all.

Remember this

Generics are a stencil, bounds are the fine print. The stencil fits any shape, but the fine print says what the shape has to be able to do.

items[0] panics on an empty slice. The homework's version returns Option<T> instead; ask the room how they'd write that (hint: items.first()?).

Bounds matter

The compiler only trusts what you promised

Fails on purpose (E0369). Press Run and read the error.

fn largest<T>(items: &[T]) -> &T {
    let mut best = &items[0];
    for item in items {
        if item > best {
            best = item;
        }
    }
    best
}

fn main() {
    println!("{}", largest(&[87, 42, 99]));
}

Without a bound, T could be anything, including types that can't be compared, so > isn't allowed (E0369). The error message suggests the fix: add T: PartialOrd.

This is the key difference from C++ templates: Rust checks the generic body once, against the bounds, not later against each use. The errors appear where you wrote the function, not three files away.

Generic types

Structs can be generic too

#[derive(Debug)]
struct Pair<T> {
    left: T,
    right: T,
}

impl<T: PartialOrd> Pair<T> {
    fn bigger(&self) -> &T {
        if self.left >= self.right {
            &self.left
        } else {
            &self.right
        }
    }
}

fn main() {
    let arms = Pair {
        left: 40,
        right: 72,
    };
    let names = Pair {
        left: "Robbie",
        right: "Zippy",
    };
    println!("{arms:?} -> {}", arms.bigger());
    println!("{names:?} -> {}", names.bigger());
}

You've used generic types all along: Vec<T>, Option<T>, Result<T, E>, HashMap<K, V>. An impl block can add bounds, so bigger only exists when T can be compared.

Option is literally enum Option<T> { Some(T), None }. Seeing that after Session 3 is a nice moment. The where clause version of bounds is in the handbook.

Trait objects

Different types in one list

trait Speak {
    fn speak(&self) -> String;
}

struct Robot;
struct Drone;
struct Vacuum;

impl Speak for Robot {
    fn speak(&self) -> String {
        "beep".into()
    }
}
impl Speak for Drone {
    fn speak(&self) -> String {
        "bzzzz".into()
    }
}
impl Speak for Vacuum {
    fn speak(&self) -> String {
        "vrrrm".into()
    }
}

fn main() {
    // one Vec, three different types: each lives in a Box behind the trait
    let studio: Vec<Box<dyn Speak>> = vec![Box::new(Robot), Box::new(Drone), Box::new(Vacuum)];
    for thing in &studio {
        println!("{}", thing.speak());
    }
}

A Vec holds one type. Box<dyn Speak> is that one type: "a box holding something that can speak". Each call looks up the right method at runtime. You've seen Box<dyn Error> already; Session 5 opens up Box properly.

Closures

Little functions you write on the spot

fn main() {
    let double = |n: u32| n * 2;
    println!("{}", double(21));

    // a closure can use variables from where it was written
    let limit = 50;
    let too_rusty = |rust: u8| rust > limit;
    println!("{} {}", too_rusty(32), too_rusty(72));

    // closures are how you customise library functions
    let mut parts = vec!["knee", "antenna", "elbow"];
    parts.sort_by_key(|p| p.len());
    println!("{parts:?}");
}

A closure is an unnamed function, written |args| body. It can use variables from around it, like limit. That's what makes them perfect for telling library functions what to do: how to sort, what to keep, what to change.

Python folks: lambdas, but with full blocks allowed. JavaScript folks: arrow functions. The types of the parameters are usually inferred.

Closures that change things

Fn, FnMut, FnOnce

fn main() {
    let mut squeaks = 0;
    // this closure changes squeaks, so it has to be mut itself
    let mut walk = |steps: u32| {
        squeaks += steps / 2;
    };
    walk(4);
    walk(6);
    println!("{squeaks} squeaks so far");
}
// returns "some closure that takes a u32 and gives a u32"
fn make_charger(percent: u32) -> impl Fn(u32) -> u32 {
    move |battery| (battery + percent).min(100)
}

fn main() {
    let quick = make_charger(10);
    let full = make_charger(100);
    println!("{} {} {}", quick(50), quick(95), full(3));
}
TraitThe closure...Call it
Fnonly reads what it capturedas often as you like
FnMutchanges what it capturedas often as you like, needs mut
FnOnceuses up (moves out) what it capturedonce

move makes a closure take ownership of what it uses, so it can outlive the function that made it.

Same three-way split as self, &self, &mut self. Every closure is FnOnce; the ones that don't consume are also FnMut; the ones that don't mutate are also Fn. move matters most in Session 5, when closures run on other threads.

Iterators

Say what you want, not how to loop

fn main() {
    let readings = [87, 12, 99, 45, 3, 76];

    let low: Vec<i32> = readings.iter().filter(|&&r| r < 50).copied().collect();
    let total: i32 = readings.iter().sum();
    let doubled: Vec<i32> = readings.iter().map(|r| r * 2).collect();
    let any_critical = readings.iter().any(|&r| r < 5);

    println!("low: {low:?}");
    println!("total: {total}, average: {}", total / readings.len() as i32);
    println!("doubled: {doubled:?}");
    println!("any critical? {any_critical}");
}

An iterator hands out items one at a time. Adapters like filter and map build a pipeline; consumers like collect, sum and any run it.

Remember this

Iterators are a conveyor belt. filter is the inspector, map is the paint shop, collect is the box at the end. Nothing moves until someone switches the belt on.

.iter() borrows items, .into_iter() takes them, .iter_mut() lets you change them. Same three choices as Session 2. The |&&r| pattern in filter is ugly; it's there because filter gets a reference to the item, which is itself a reference. .copied() tidies it.

Iterators are lazy

Nothing happens until someone asks

fn main() {
    let parts = ["knee", "elbow", "antenna", "visor", "toe"];
    // nothing happens until something asks for items
    let checked = parts.iter().map(|p| {
        println!("  checking {p}");
        p.len()
    });
    println!("built the iterator, nothing checked yet");
    let first_two: Vec<usize> = checked.take(2).collect();
    println!("lengths: {first_two:?}");
}

Building the pipeline does no work. take(2) plus collect asks for two items, so only two parts get checked. This is why iterator chains are as fast as hand-written loops, and sometimes faster.

If you build an iterator and never consume it, the compiler warns "iterators are lazy and do nothing unless consumed". Show that by deleting the collect line.

The adapter toolbox

enumerate, zip, rev, fold and friends

fn main() {
    let parts = ["knee", "elbow", "antenna"];
    let rust = [60, 35, 15];

    for (i, p) in parts.iter().enumerate() {
        println!("{}. {p}", i + 1);
    }
    let pairs: Vec<(&str, i32)> = parts.iter().copied().zip(rust).collect();
    println!("{pairs:?}");

    let worst = pairs.iter().max_by_key(|(_, r)| *r);
    println!("worst: {worst:?}");

    let sentence = parts
        .iter()
        .rev()
        .fold(String::new(), |acc, p| acc + p + " ");
    println!("backwards: {}", sentence.trim_end());

    let countdown: Vec<u32> = (1..=10).rev().step_by(3).collect();
    println!("{countdown:?}");
}

You don't need to memorize these. You need to know they exist, so you reach for the docs instead of writing a loop with three counters. The handbook's cheat sheet lists the common ones.

Spend a minute on fold: an accumulator and a closure, the general version that sum and collect are special cases of. max_by_key with a tuple pattern in the closure is lab-relevant.

Lifetimes, properly

Which input does the answer borrow from?

Fails on purpose (E0106). Press Run and read the error.

fn longer(a: &str, b: &str) -> &str {
    if a.len() >= b.len() { a } else { b }
}

fn main() {
    println!("{}", longer("knee", "antenna"));
}

The function returns a reference, but from a or b? The compiler can't guess, so it asks (E0106). A lifetime annotation answers:

// 'a says: the answer lives no longer than the shorter-lived of a and b
fn longer<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

fn main() {
    let part = String::from("antenna");
    let answer = longer("knee", &part);
    println!("{answer}");
}

'a doesn't change how long anything lives. It's a label that ties the output to the inputs, so the compiler can check every caller.

Lifetime elision rules: with one reference input, or a &self method, the output borrows from that and you write nothing. Two reference inputs and a reference output: you have to say. Session 2 said "lifetimes come later"; this is later.

Lifetimes catch real bugs

The answer can't outlive its source

Fails on purpose (E0597). Press Run and read the error.

fn longer<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

fn main() {
    let answer;
    let knee = String::from("knee");
    {
        let antenna = String::from("antenna");
        answer = longer(&knee, &antenna);
    } // antenna is dropped here...
    println!("{answer}"); // ...but answer might point into it
}

Because longer said the answer lives no longer than both inputs, the compiler knows answer might point into antenna, which is dropped too soon (E0597). In C this compiles and crashes on a Tuesday.

// a struct that borrows text instead of owning it
struct Excerpt<'a> {
    line: &'a str,
}

impl<'a> Excerpt<'a> {
    fn first_word(&self) -> &'a str {
        self.line.split_whitespace().next().unwrap_or("")
    }
}

fn main() {
    let log = String::from("SQUEAK detected in left knee. Again.");
    let first_line = Excerpt {
        line: log.split('.').next().unwrap_or(""),
    };
    println!("{} / {}", first_line.line, first_line.first_word());
}

A struct that holds a reference needs a lifetime too: an Excerpt can't outlive the text it borrows.

Lab step 5 is next_in_room<'a>(tasks: &'a [Task], room: &str) -> Option<&'a Task>. Ask why room doesn't need 'a: the answer never borrows from it. The lab has a test where room is dropped before the answer is used.
