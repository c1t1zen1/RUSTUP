1. Box

A smart pointer is a value that points at data and also owns or manages it. The simplest is Box<T>: it moves one value to the heap and owns it. When the Box goes, the value goes.

fn main() {
    // A Box puts one value on the heap and owns it. The Box itself is just a pointer.
    let battery = Box::new(87_u32);
    println!("battery: {battery}%"); // a Box acts like the value inside it
    println!("plus 10: {}", *battery + 10); // * reaches in when you need to

    let spare: Box<[u8; 1000]> = Box::new([0; 1000]); // a big value, kept off the stack
    println!("spare parts bin holds {} slots", spare.len());
} // both Boxes are dropped here, and the heap memory goes with them

You need a Box when a type would contain itself. The compiler can't size a Route that holds a Route:

Fails on purpose (E0072). Press Run and read the error.

// A route is either the end, or one step followed by the rest of the route.
#[derive(Debug)]
enum Route {
    Step(char, Route),
    End,
}

fn main() {
    let r = Route::Step('N', Route::End);
    println!("{r:?}");
}

A Box is always one pointer wide, so boxing the inner one fixes it:

#[derive(Debug)]
enum Route {
    Step(char, Box<Route>), // a Box has a known size, so Route does too
    End,
}

fn letters(r: &Route) -> String {
    match r {
        Route::Step(c, rest) => format!("{c}{}", letters(rest)),
        Route::End => String::new(),
    }
}

fn main() {
    let r = Route::Step('N', Box::new(Route::Step('E', Box::new(Route::End))));
    println!("{r:?}");
    println!("route: {}", letters(&r));
}

You already used the third reason for a Box in Session 4: Box<dyn Bot>, one type that can hold any bot.

2. Rc and RefCell

Ownership has one owner. Sometimes the truth is "several things share this, and nobody knows who finishes last". Rc<T>, a reference-counted pointer, keeps a count of owners and frees the value when the count reaches zero.

use std::rc::Rc;

#[derive(Debug)]
struct Map {
    name: String,
}

fn main() {
    // Three bots, one map. Nobody can say which bot finishes with it last.
    let studio = Rc::new(Map {
        name: String::from("studio floor plan"),
    });
    let robbie = Rc::clone(&studio); // not a copy of the map, just one more owner
    let zippy = Rc::clone(&studio);

    println!(
        "{} owners of the {}",
        Rc::strong_count(&studio),
        robbie.name
    );
    drop(zippy);
    println!("{} owners after Zippy leaves", Rc::strong_count(&studio));
} // the last owner goes, and the map is freed
Remember this

Rc is a library card. Many people can borrow the book, and it goes back on the shelf when the last card is handed in. Rc::clone(&x) makes a new card, not a new book.

An Rc only gives shared access, so you can't change what's inside. RefCell<T> fixes that by moving the borrow check from compile time to run time. borrow() gives a shared borrow, borrow_mut() a mutable one:

use std::cell::RefCell;
use std::rc::Rc;

fn main() {
    // One shared log that several owners can write to.
    let log = Rc::new(RefCell::new(Vec::new()));
    let robbie_log = Rc::clone(&log);
    let zippy_log = Rc::clone(&log);

    robbie_log.borrow_mut().push("Robbie: oiled left knee");
    zippy_log.borrow_mut().push("Zippy: filmed the oiling");
    robbie_log.borrow_mut().push("Robbie: knee still squeaks");

    for line in log.borrow().iter() {
        println!("{line}");
    }
}

The rules are the same as ever: many readers or one writer. Break them and the program panics instead of failing to compile:

Compiles, then panics on purpose. Press Run and read the message.

use std::cell::RefCell;

fn main() {
    let parts = RefCell::new(vec!["knee", "elbow"]);
    let reading = parts.borrow(); // a shared borrow, checked at run time
    parts.borrow_mut().push("antenna"); // a &mut while it's still alive: panic
    println!("{reading:?}");
}

If you'd rather check than panic, try_borrow_mut() returns a Result:

use std::cell::RefCell;

fn main() {
    let battery = RefCell::new(72);
    let reading = battery.borrow();
    match battery.try_borrow_mut() {
        Ok(mut b) => *b -= 10,
        Err(_) => println!("busy: someone is still reading the battery"),
    }
    println!("battery: {reading}%");
}
Gotcha

Keep RefCell borrows short. Borrow, use, and let the borrow drop on the same line. A borrow kept in a variable is the usual cause of "already borrowed".

3. Threads and move

A thread is a second line of work running at the same time as the first. thread::spawn starts one with a closure and returns a JoinHandle. join() waits for it to finish and hands back what the closure returned.

use std::thread;
use std::time::Duration;

fn main() {
    let handle = thread::spawn(|| {
        for i in 1..=3 {
            println!("  helper Robbie: sweep {i}");
            thread::sleep(Duration::from_millis(10));
        }
        "floor swept" // the thread's answer
    });

    for i in 1..=3 {
        println!("main Robbie: polish {i}");
        thread::sleep(Duration::from_millis(10));
    }

    let answer = handle.join().unwrap(); // wait for it, and get its answer
    println!("helper says: {answer}");
}

Run it twice: the lines come out in a different order. Threads run whenever the operating system lets them, so never write a test that depends on which thread finishes first.

A new thread might outlive the function that started it, so it can't borrow that function's local variables:

Fails on purpose (E0373). Press Run and read the error.

use std::thread;

fn main() {
    let rooms = vec!["studio", "workshop"];
    let handle = thread::spawn(|| {
        println!("scanning {rooms:?}"); // borrows rooms, but main might drop it first
    });
    handle.join().unwrap();
}

A move closure takes ownership of what it uses, so nothing can dangle:

use std::thread;

fn main() {
    let rooms = vec!["studio", "workshop"];
    let handle = thread::spawn(move || {
        // move: the thread owns rooms now, so it can't dangle
        println!("scanning {rooms:?}");
        rooms.len()
    });
    println!("scanned {} rooms", handle.join().unwrap());
}
Remember this

A thread packs its own suitcase. move means "take it with you". If you still need it at home, pack a clone.

4. Channels

The easiest way for threads to cooperate is to not share anything at all, just send results. mpsc::channel() gives a sender tx and a receiver rx. mpsc stands for multiple producer, single consumer: clone the sender for as many threads as you like, and keep one receiver.

use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel(); // tx sends, rx receives

    for name in ["Robbie", "Zippy", "Dusty"] {
        let tx = tx.clone(); // one sender per thread
        thread::spawn(move || {
            tx.send(format!("{name}: room clear")).unwrap();
        });
    }
    drop(tx); // drop the first sender too, or the loop below never ends

    for msg in rx {
        // waits for each message, stops when every sender is gone
        println!("{msg}");
    }
}

send moves the value into the channel, so the sender can't touch it afterwards. Looping over rx waits for each message and ends when every sender has been dropped.

Gotcha

If your loop over rx never ends, a sender is still alive. Usually it's the first tx, still sitting in main. drop(tx) after the spawning loop.

5. Arc and Mutex

When threads really must share one changing value, you need two things. Arc<T> is Rc with an atomic counter, safe to update from many threads at once. Mutex<T> lets only one thread at a time reach the value inside.

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let squeaks = Arc::new(Mutex::new(0)); // shared and safe to change
    let mut handles = Vec::new();

    for _ in 0..4 {
        let squeaks = Arc::clone(&squeaks);
        handles.push(thread::spawn(move || {
            for _ in 0..100 {
                *squeaks.lock().unwrap() += 1; // lock, change, unlock at the ;
            }
        }));
    }
    for h in handles {
        h.join().unwrap();
    }
    println!("total squeaks: {}", squeaks.lock().unwrap());
}

lock() waits until no one else holds the lock, then gives you a guard. The guard acts like &mut T, and unlocks when it's dropped. Use a block or a single statement to keep the lock short:

use std::sync::Mutex;

fn main() {
    let floor = Mutex::new(vec![3, 1, 4]);
    {
        let mut tiles = floor.lock().unwrap(); // locked from here...
        tiles[0] -= 1;
        tiles[2] -= 1;
    } // ...to here, where the guard is dropped
    let dirt: u32 = floor.lock().unwrap().iter().sum(); // locked for one line
    println!("dirt left: {dirt}");
}
Remember this

A Mutex is the bathroom key on a giant spanner. One at a time, hand it back quickly, and never take two keys in different orders, or two bots wait for each other forever. That's a deadlock, and Rust can't stop it for you.

6. Send and Sync

How does Rust know Rc isn't safe on another thread? Two marker traits, with no methods at all:

  • Send: a value of this type can be moved to another thread.
  • Sync: a reference to this type can be shared between threads.

The compiler works them out for every type: a struct is Send if all its fields are. Rc isn't, because its counter isn't atomic, and thread::spawn demands Send:

Fails on purpose (E0277). Press Run and read the error.

use std::rc::Rc;
use std::thread;

fn main() {
    let map = Rc::new(String::from("studio floor plan"));
    let copy = Rc::clone(&map);
    thread::spawn(move || {
        println!("{copy}");
    })
    .join()
    .unwrap();
}

The error is long, but its first line says it all: Rc<String> cannot be sent between threads safely. Swap Rc for Arc and it compiles. This is why people call it fearless concurrency: a data race is a type error.

7. Scoped threads

Threads started inside thread::scope are all joined before it returns, so they can safely borrow local data. No move, no Arc:

use std::thread;

fn main() {
    let readings = vec![12, 40, 7, 33, 21, 9];
    let (left, right) = readings.split_at(readings.len() / 2);

    // Scoped threads must finish before scope returns, so they may borrow.
    let total = thread::scope(|s| {
        let a = s.spawn(|| left.iter().sum::<u32>());
        let b = s.spawn(|| right.iter().sum::<u32>());
        a.join().unwrap() + b.join().unwrap()
    });
    println!("total dust: {total}, and readings is still ours: {readings:?}");
}

This is the neatest way to split one job across cores, and it's step 4 of the lab.

8. Async with tokio

A thread is a whole extra worker, with its own stack. That's fine for a few hundred, but a server with ten thousand open connections, each mostly waiting, needs something lighter. That's async.

An async fn doesn't run when you call it. It returns a future, a plan, and nothing happens until you .await it:

async fn beep() {
    println!("beep!");
}

#[tokio::main]
async fn main() {
    let later = beep(); // nothing happens yet: a future is a plan, not an action
    println!("plan made");
    later.await; // now it runs
    beep().await;
}

A runtime runs futures, switching to another whenever one is waiting. Rust doesn't ship one; tokio is the usual choice:

[dependencies]
tokio = { version = "1", features = ["full"] }

tokio::join! runs several futures at once and waits for all of them:

use std::time::Duration;
use tokio::time::sleep;

async fn scan(room: &str, ms: u64) -> String {
    sleep(Duration::from_millis(ms)).await; // waiting, without blocking a thread
    format!("{room}: clear")
}

#[tokio::main]
async fn main() {
    // join! runs all three at once and waits for every one.
    let (a, b, c) = tokio::join!(scan("studio", 30), scan("workshop", 10), scan("roof", 20));
    println!("{a} | {b} | {c}");
}

tokio::spawn starts an independent task, the async version of a thread:

use std::time::Duration;
use tokio::time::sleep;

#[tokio::main]
async fn main() {
    let mut tasks = Vec::new();
    for (i, room) in ["studio", "workshop", "lobby"].into_iter().enumerate() {
        // spawn starts a task right away, like thread::spawn but far cheaper
        tasks.push(tokio::spawn(async move {
            sleep(Duration::from_millis(10 * (3 - i as u64))).await;
            room.len()
        }));
    }
    let mut total = 0;
    for t in tasks {
        total += t.await.unwrap(); // a JoinHandle you .await instead of join()
    }
    println!("{total} letters of rooms scanned");
}
Gotcha

Inside async code, use tokio::time::sleep(..).await, never std::thread::sleep. The std version blocks the whole worker thread, so every other task on it stops too.

9. Testing

You've run cargo test since Session 1. Now you write the tests. A test is a function marked #[test] that passes if it returns without panicking, so assert! and assert_eq! are all you need.

/// Percent of a battery left after `minutes` of work, never below 0.
pub fn battery_after(start: u32, minutes: u32) -> u32 {
    start.saturating_sub(minutes / 2)
}

fn main() {
    println!("{}% left", battery_after(80, 30));
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn drains_one_percent_per_two_minutes() {
        assert_eq!(battery_after(80, 30), 65);
    }

    #[test]
    fn never_goes_negative() {
        assert_eq!(battery_after(10, 500), 0);
    }

    #[test]
    #[should_panic]
    fn indexing_past_the_end_panics() {
        let parts = [1, 2, 3];
        let _ = parts[parts.len()];
    }
}
  • #[cfg(test)] means the module is only compiled for cargo test.
  • use super::*; brings in everything from the file above, private items included.
  • #[should_panic] passes only if the test panics: use it to check that bad input is refused.

Tests in the tests/ folder are integration tests. They use your crate from the outside, like a real user, so they only see pub items. Every lab and homework's tests live there. Examples inside /// doc comments are compiled and run too, so your docs can't go stale.

cargo test                   # everything
cargo test step3             # only tests whose name contains step3
cargo test --test mine       # only tests/mine.rs
cargo test -- --nocapture    # show println! output
Remember this

A test name is the rule it checks. never_goes_negative tells you what broke. test2 doesn't.

10. serde and JSON

serde turns your structs into JSON, TOML, YAML and more, and back again. Two derives do almost all of the work:

[dependencies]
serde = { version = "1", features = ["derive"] }
serde_json = "1"
use serde::{Deserialize, Serialize};

#[derive(Debug, Serialize, Deserialize)]
struct Bot {
    name: String,
    rust: u8,
    parts: Vec<String>,
}

fn main() -> Result<(), serde_json::Error> {
    let robbie = Bot {
        name: String::from("Robbie"),
        rust: 72,
        parts: vec![String::from("chest plate"), String::from("left knee")],
    };
    let text = serde_json::to_string_pretty(&robbie)?; // struct to JSON
    println!("{text}");

    let back: Bot = serde_json::from_str(r#"{"name":"Zippy","rust":3,"parts":[]}"#)?; // and back
    println!("{back:?}");

    let broken: Result<Bot, _> = serde_json::from_str(r#"{"name":"Dusty"}"#);
    println!("{}", broken.unwrap_err()); // a missing field is an error, not a guess
    Ok(())
}
  • serde_json::to_string_pretty(&value) writes JSON. serde_json::from_str::<T>(text) reads it.
  • A missing or wrongly typed field is an Err with a clear message, never a silent guess.
  • Tuples like (usize, usize) read and write as JSON arrays: [2, 1].
  • Turn serde's error into your own with map_err, then ? as usual.

Practice questions

1. Why does enum List { Node(i32, List), End } fail, and what fixes it?

A List would contain a whole List, so it has no fixed size (E0072). Node(i32, Box<List>) fixes it, because a Box is always one pointer wide.

2. What does Rc::clone(&map) copy?

Nothing big. It adds an owner and increases the reference count. The map itself is shared, not copied.

3. A program compiles but panics with "already borrowed". What happened?

A RefCell was borrowed mutably while another borrow of it was still alive. The borrow rules are checked at run time for RefCell.

4. Why does the compiler suggest move when a spawned closure uses a local variable?

The thread could outlive the function, so a borrow could dangle (E0373). move gives the thread ownership.

5. A loop for msg in rx never ends, though every thread has finished. Why?

A sender is still alive, usually the original tx in the main thread. Drop it after spawning.

6. Which type do you use for a counter that eight threads all increase?

Arc<Mutex<u32>>: Arc to share it across threads, Mutex to change it one thread at a time. (An AtomicU32 also works for a plain counter.)

7. Why can't an Rc be sent to another thread?

Its reference count isn't atomic, so two threads changing it at once could corrupt it. Rc isn't Send, and thread::spawn requires Send (E0277).

8. What's the advantage of thread::scope over thread::spawn?

Scoped threads are joined before the scope returns, so they can borrow local data without move or Arc.

9. You call an async fn but nothing happens. What did you forget?

.await. Calling it only creates a future; awaiting it runs it.

10. What does #[cfg(test)] on a module do?

The module is only compiled when you run cargo test, so test code never ends up in your real program.
