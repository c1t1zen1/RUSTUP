The big idea

Sharing is the hard part

One Robbie can't scan five rooms before it rains. Five Robbies can, if they don't trip over each other.

Two bots writing the same tally at the same moment is a data race. In most languages it's a bug you find on a Friday night. In Rust it doesn't compile.

Remember this

Many readers or one writer, now across threads. The rule from Session 2 didn't change. Today's types are the tools for following it when ownership gets complicated.

Concurrency means juggling several jobs; parallelism means doing them literally at the same time on different cores. Threads give both, async gives cheap concurrency. Everything today is a way to answer "who owns this, and who may change it?" when one owner isn't enough.

Box

One value on the heap

fn main() {
    // A Box puts one value on the heap and owns it. The Box itself is just a pointer.
    let battery = Box::new(87_u32);
    println!("battery: {battery}%"); // a Box acts like the value inside it
    println!("plus 10: {}", *battery + 10); // * reaches in when you need to

    let spare: Box<[u8; 1000]> = Box::new([0; 1000]); // a big value, kept off the stack
    println!("spare parts bin holds {} slots", spare.len());
} // both Boxes are dropped here, and the heap memory goes with them
  • Box::new(x) moves x to the heap. The Box is a pointer that owns it.
  • It behaves like the value inside. * reaches in when you need it.
  • You met it in Session 4: Box<dyn Bot> held different bots in one Vec.
Three reasons to box: a value whose size isn't known at compile time (dyn Trait, recursive types), a big value you don't want to copy around on the stack, and handing over ownership of a trait object. A Box is freed when its owner goes out of scope, same as any value.

Box for recursive types

A type that contains itself

Fails on purpose (E0072). Press Run and read the error.

// A route is either the end, or one step followed by the rest of the route.
#[derive(Debug)]
enum Route {
    Step(char, Route),
    End,
}

fn main() {
    let r = Route::Step('N', Route::End);
    println!("{r:?}");
}

A Route holds a Route, which holds a Route... The compiler can't work out its size (E0072). Put the inner one in a Box, which is always one pointer wide:

#[derive(Debug)]
enum Route {
    Step(char, Box<Route>), // a Box has a known size, so Route does too
    End,
}

fn letters(r: &Route) -> String {
    match r {
        Route::Step(c, rest) => format!("{c}{}", letters(rest)),
        Route::End => String::new(),
    }
}

fn main() {
    let r = Route::Step('N', Box::new(Route::Step('E', Box::new(Route::End))));
    println!("{r:?}");
    println!("route: {}", letters(&r));
}
This is a linked list, and you'll rarely write one in real Rust (Vec is almost always better). But trees, parsers and expression evaluators all need it. The error message itself suggests the Box fix; point that out.

Rc

More than one owner

use std::rc::Rc;

#[derive(Debug)]
struct Map {
    name: String,
}

fn main() {
    // Three bots, one map. Nobody can say which bot finishes with it last.
    let studio = Rc::new(Map {
        name: String::from("studio floor plan"),
    });
    let robbie = Rc::clone(&studio); // not a copy of the map, just one more owner
    let zippy = Rc::clone(&studio);

    println!(
        "{} owners of the {}",
        Rc::strong_count(&studio),
        robbie.name
    );
    drop(zippy);
    println!("{} owners after Zippy leaves", Rc::strong_count(&studio));
} // the last owner goes, and the map is freed

Rc is a reference-counted pointer. Rc::clone doesn't copy the map, it adds an owner and bumps the count. When the last owner goes, the map is freed.

Remember this

Rc is a library card. Many people can borrow the book. It goes back on the shelf when the last card is handed in. Rc is read-only, and single-thread only.

Write Rc::clone(&x), not x.clone(): both work, but the first tells the reader it's cheap. Rc can leak with cycles (a parent and child pointing at each other); Weak breaks cycles. Mention it, don't teach it.

RefCell

Change it anyway, checked at run time

use std::cell::RefCell;
use std::rc::Rc;

fn main() {
    // One shared log that several owners can write to.
    let log = Rc::new(RefCell::new(Vec::new()));
    let robbie_log = Rc::clone(&log);
    let zippy_log = Rc::clone(&log);

    robbie_log.borrow_mut().push("Robbie: oiled left knee");
    zippy_log.borrow_mut().push("Zippy: filmed the oiling");
    robbie_log.borrow_mut().push("Robbie: knee still squeaks");

    for line in log.borrow().iter() {
        println!("{line}");
    }
}

Rc only hands out shared access. Wrap the value in a RefCell and you can borrow_mut() through a shared pointer. The borrow rules still apply, but they're checked while the program runs:

Compiles, then panics on purpose. Press Run and read the message.

use std::cell::RefCell;

fn main() {
    let parts = RefCell::new(vec!["knee", "elbow"]);
    let reading = parts.borrow(); // a shared borrow, checked at run time
    parts.borrow_mut().push("antenna"); // a &mut while it's still alive: panic
    println!("{reading:?}");
}
This is "interior mutability". RefCell trades a compile-time error for a run-time panic ("already borrowed"), so keep borrows short: borrow, use, let it drop on the same line. Rc<RefCell<T>> is the single-thread "shared and changeable" combo; Arc<Mutex<T>> is the thread version, coming up.

Box owns, Rc shares, RefCell lets you change, and A means Atomic: safe across threads. Read the type from outside in: Arc<Mutex<u32>> is "shared across threads, a lock, a number".

Leave this slide up during the lab. The question to ask every time: how many owners, how many threads, does anyone change it? Three answers, one cell of the table.

Threads

A second Robbie, right now

use std::thread;
use std::time::Duration;

fn main() {
    let handle = thread::spawn(|| {
        for i in 1..=3 {
            println!("  helper Robbie: sweep {i}");
            thread::sleep(Duration::from_millis(10));
        }
        "floor swept" // the thread's answer
    });

    for i in 1..=3 {
        println!("main Robbie: polish {i}");
        thread::sleep(Duration::from_millis(10));
    }

    let answer = handle.join().unwrap(); // wait for it, and get its answer
    println!("helper says: {answer}");
}
  • thread::spawn runs a closure on a new thread and returns a JoinHandle.
  • join() waits for it and gives back what the closure returned.
  • The lines interleave differently on every run. That's normal, and it's why tests must never depend on thread order.
Press Run twice and compare the output order. When main returns, the whole program ends, including unfinished threads: that's why we join. A thread costs a few kilobytes to megabytes of stack and an OS call to start, so thousands are fine, millions aren't (which is where async comes in).

move closures

The thread takes its things with it

Fails on purpose (E0373). Press Run and read the error.

use std::thread;

fn main() {
    let rooms = vec!["studio", "workshop"];
    let handle = thread::spawn(|| {
        println!("scanning {rooms:?}"); // borrows rooms, but main might drop it first
    });
    handle.join().unwrap();
}

The thread might outlive main's rooms, so borrowing it is refused (E0373). Add move and the thread owns it:

use std::thread;

fn main() {
    let rooms = vec!["studio", "workshop"];
    let handle = thread::spawn(move || {
        // move: the thread owns rooms now, so it can't dangle
        println!("scanning {rooms:?}");
        rooms.len()
    });
    println!("scanned {} rooms", handle.join().unwrap());
}
The error message suggests move, exactly. After the move, main can't use rooms any more (Session 2: ownership moved). If main still needs it, clone it first and move the clone, or use scoped threads (a few slides on).

Channels

Pass messages, not memory

use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel(); // tx sends, rx receives

    for name in ["Robbie", "Zippy", "Dusty"] {
        let tx = tx.clone(); // one sender per thread
        thread::spawn(move || {
            tx.send(format!("{name}: room clear")).unwrap();
        });
    }
    drop(tx); // drop the first sender too, or the loop below never ends

    for msg in rx {
        // waits for each message, stops when every sender is gone
        println!("{msg}");
    }
}

mpsc::channel() gives a sender and a receiver: multiple producer, single consumer. Clone the sender for each thread. Looping over the receiver waits for each message and ends when every sender is gone.

Remember this

Drop the first sender. If your loop over rx never ends, the original tx is still alive in main.

Go's proverb: don't communicate by sharing memory; share memory by communicating. send() moves the value into the channel, so the sending thread can't touch it afterwards. That's why channels can't race. Lab step 2 has this exact hang as a trap.

Arc and Mutex

One counter, many hands

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let squeaks = Arc::new(Mutex::new(0)); // shared and safe to change
    let mut handles = Vec::new();

    for _ in 0..4 {
        let squeaks = Arc::clone(&squeaks);
        handles.push(thread::spawn(move || {
            for _ in 0..100 {
                *squeaks.lock().unwrap() += 1; // lock, change, unlock at the ;
            }
        }));
    }
    for h in handles {
        h.join().unwrap();
    }
    println!("total squeaks: {}", squeaks.lock().unwrap());
}
  • Arc is Rc with an atomic count, so it's safe to share across threads.
  • Mutex lets one thread at a time in. lock() waits your turn and hands you a guard.
  • The guard unlocks when it's dropped. Here that's at the end of the statement.
Four threads, a hundred bumps each, always exactly 400. Ask the room what C would print without the lock (anything up to 400). lock() returns a Result because a thread that panicked while holding the lock "poisons" it; unwrap is fine in class. Deadlock is still possible: two locks taken in different orders. Rust stops races, not deadlocks.

Send and Sync

Why Rc can't go to another thread

Fails on purpose (E0277). Press Run and read the error.

use std::rc::Rc;
use std::thread;

fn main() {
    let map = Rc::new(String::from("studio floor plan"));
    let copy = Rc::clone(&map);
    thread::spawn(move || {
        println!("{copy}");
    })
    .join()
    .unwrap();
}

Rc's counter isn't atomic, so two threads could corrupt it. Rust marks it as not Send, and thread::spawn requires Send (E0277). Swap in Arc and it compiles.

  • Send: safe to move to another thread.
  • Sync: safe to share by reference between threads.
  • The compiler works both out for your own types. You almost never write them.
These are marker traits: no methods, just a promise. A struct is Send if all its fields are. That's the "fearless" part: the compiler tracks thread safety through every type you build. Lab README asks students to make this exact mistake once, on purpose.

Scoped threads

Borrow, as long as everyone's home by dinner

use std::thread;

fn main() {
    let readings = vec![12, 40, 7, 33, 21, 9];
    let (left, right) = readings.split_at(readings.len() / 2);

    // Scoped threads must finish before scope returns, so they may borrow.
    let total = thread::scope(|s| {
        let a = s.spawn(|| left.iter().sum::<u32>());
        let b = s.spawn(|| right.iter().sum::<u32>());
        a.join().unwrap() + b.join().unwrap()
    });
    println!("total dust: {total}, and readings is still ours: {readings:?}");
}

Threads started inside thread::scope must finish before it returns, so they can borrow local data. No move, no Arc, and readings is still yours afterwards.

thread::scope is newer (Rust 1.63) and is often the cleanest answer for "split this work across cores". Lab step 4 uses it with chunks(). The scope joins any thread you didn't join yourself.

Async

Waiting without a thread each

async fn beep() {
    println!("beep!");
}

#[tokio::main]
async fn main() {
    let later = beep(); // nothing happens yet: a future is a plan, not an action
    println!("plan made");
    later.await; // now it runs
    beep().await;
}

An async fn returns a future: a plan to do something. Nothing runs until you .await it. A runtime like tokio runs thousands of futures on a few threads, switching whenever one is waiting.

Futures are lazy, like iterators in Session 4. The classic beginner bug is calling an async fn and forgetting .await; the compiler warns "unused future". #[tokio::main] turns main into an async fn and starts the runtime. These run on the Playground because tokio is one of its preinstalled crates.

tokio

Three scans, one wait

use std::time::Duration;
use tokio::time::sleep;

async fn scan(room: &str, ms: u64) -> String {
    sleep(Duration::from_millis(ms)).await; // waiting, without blocking a thread
    format!("{room}: clear")
}

#[tokio::main]
async fn main() {
    // join! runs all three at once and waits for every one.
    let (a, b, c) = tokio::join!(scan("studio", 30), scan("workshop", 10), scan("roof", 20));
    println!("{a} | {b} | {c}");
}

tokio::join! runs several futures at once and waits for all of them. The whole thing takes about as long as the slowest scan, not the sum.

[dependencies]
tokio = { version = "1", features = ["full"] }
Use tokio::time::sleep, never std::thread::sleep, inside async code: the std one blocks the whole worker thread, so every other task on it stops too. Same for heavy CPU work; that belongs on spawn_blocking or a plain thread.

tokio::spawn

Tasks: threads that cost almost nothing

use std::time::Duration;
use tokio::time::sleep;

#[tokio::main]
async fn main() {
    let mut tasks = Vec::new();
    for (i, room) in ["studio", "workshop", "lobby"].into_iter().enumerate() {
        // spawn starts a task right away, like thread::spawn but far cheaper
        tasks.push(tokio::spawn(async move {
            sleep(Duration::from_millis(10 * (3 - i as u64))).await;
            room.len()
        }));
    }
    let mut total = 0;
    for t in tasks {
        total += t.await.unwrap(); // a JoinHandle you .await instead of join()
    }
    println!("{total} letters of rooms scanned");
}

Testing

Tests live next to the code

/// Percent of a battery left after `minutes` of work, never below 0.
pub fn battery_after(start: u32, minutes: u32) -> u32 {
    start.saturating_sub(minutes / 2)
}

fn main() {
    println!("{}% left", battery_after(80, 30));
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn drains_one_percent_per_two_minutes() {
        assert_eq!(battery_after(80, 30), 65);
    }

    #[test]
    fn never_goes_negative() {
        assert_eq!(battery_after(10, 500), 0);
    }

    #[test]
    #[should_panic]
    fn indexing_past_the_end_panics() {
        let parts = [1, 2, 3];
        let _ = parts[parts.len()];
    }
}
cargo test                  # every test
cargo test never_goes       # only tests whose name matches
cargo test -- --nocapture   # show println! output from tests
#[cfg(test)] means the module only exists when testing, so test helpers never ship. use super::* brings the outer functions in. Press Run here and you get main; cargo test runs the three tests. should_panic tests that something panics; it's how you test "this must refuse".

serde

Structs to JSON and back

use serde::{Deserialize, Serialize};

#[derive(Debug, Serialize, Deserialize)]
struct Bot {
    name: String,
    rust: u8,
    parts: Vec<String>,
}

fn main() -> Result<(), serde_json::Error> {
    let robbie = Bot {
        name: String::from("Robbie"),
        rust: 72,
        parts: vec![String::from("chest plate"), String::from("left knee")],
    };
    let text = serde_json::to_string_pretty(&robbie)?; // struct to JSON
    println!("{text}");

    let back: Bot = serde_json::from_str(r#"{"name":"Zippy","rust":3,"parts":[]}"#)?; // and back
    println!("{back:?}");

    let broken: Result<Bot, _> = serde_json::from_str(r#"{"name":"Dusty"}"#);
    println!("{}", broken.unwrap_err()); // a missing field is an error, not a guess
    Ok(())
}
[dependencies]
serde = { version = "1", features = ["derive"] }
serde_json = "1"
serde is the most downloaded crate there is. #[derive(Serialize, Deserialize)] writes all the conversion code. Notice what happens with a missing field: an error with a clear message, not a silent default. #[serde(default)] opts in to defaults per field. Homework 5 reads its config this way.

Homework 5 · due Session 6

Swarm Sim

A JSON config describes a dirty floor and a few cleaning bots. Read it, check it, run every bot on its own thread over one shared floor, and write the report back out as JSON.

  • Derive serde's traits and load the config with serde_json, turning its errors into your SimError.
  • Check the floor and the bots in the documented order, with a clear message for each problem.
  • Run the bots with thread::spawn and an Arc<Mutex<..>> floor. Bumping into a wall is allowed.
  • Write at least three tests of your own.

8 visible tests, your tests, hidden edge cases, clippy and fmt: 10 points.

The hidden tests check the order of the checks, empty rows, case-sensitive names, tiles never going below zero, eight bots crowding one floor giving the same totals twenty runs in a row, and every error message. The report deliberately leaves out who cleaned what, because with threads that changes from run to run. Ask students why.
