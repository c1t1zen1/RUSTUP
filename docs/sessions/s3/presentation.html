Why build types?

Name things, or forget what they mean

struct Robot {
    name: String,
    battery: u8,
    x: i32,
    y: i32,
}

fn main() {
    // a tuple works, but which number is which?
    let mystery = (87, 3, -2);
    println!("{mystery:?}");

    // a struct says it out loud
    let robbie = Robot {
        name: String::from("Robbie"),
        battery: 87,
        x: 3,
        y: -2,
    };
    println!(
        "{} is at ({}, {}) with {}% battery",
        robbie.name, robbie.x, robbie.y, robbie.battery
    );
}

A tuple is fine for two or three things that obviously belong together. The moment you have to remember "the second number is x", give it a name. A struct is a named bundle of named fields.

Ask the room what (87, 3, -2) means. Get three different answers. That's the argument for structs. C folks: yes, it's a C struct. Python folks: it's a class with fixed fields and no inheritance.

Structs

Make one, change one, print one

#[derive(Debug)]
struct Robot {
    name: String,
    battery: u8,
}

fn main() {
    let mut robbie = Robot {
        name: String::from("Robbie"),
        battery: 40,
    };
    robbie.battery += 25; // the whole struct is mut, so every field is
    println!("{robbie:?}");
    println!("{robbie:#?}"); // pretty, one field per line
    println!("{} is at {}%", robbie.name, robbie.battery);
}
  • Mutability belongs to the binding, not the field: let mut robbie makes every field changeable.
  • #[derive(Debug)] asks the compiler to write the printing code for {:?} and {:#?}.
There's no way to mark one field mut and another not. If you need that, you'll use private fields and methods, which is three slides away. derive is a macro that writes trait implementations for you; traits get their own session next week.

Methods

impl: teach the struct some tricks

struct Robot {
    name: String,
    battery: u8,
}

impl Robot {
    // an associated function: no self, called as Robot::new
    fn new(name: &str) -> Robot {
        Robot {
            name: name.to_string(),
            battery: 100,
        }
    }

    // &self: look but don't touch
    fn is_tired(&self) -> bool {
        self.battery < 20
    }

    // &mut self: allowed to change fields
    fn work(&mut self, hours: u8) {
        self.battery = self.battery.saturating_sub(hours * 15);
    }
}

fn main() {
    let mut r = Robot::new("Robbie");
    r.work(6);
    println!("{} tired? {} ({}%)", r.name, r.is_tired(), r.battery);
}
Remember this

&self looks, &mut self touches, self takes. It's Session 2's ownership rules, wearing a method's hat. No self at all means an associated function, called with ::, like Robot::new.

Point out saturating_sub: it stops at 0 instead of underflowing a u8. Ask what would happen with plain subtraction (a panic in debug builds: "attempt to subtract with overflow"). new is just a convention; Rust has no constructors.

Struct shortcuts

Less typing, same meaning

#[derive(Debug, Clone)]
struct Part {
    name: String,
    rust: u8,
    shiny: bool,
}

#[derive(Debug)]
struct Meters(f64); // a tuple struct: a named wrapper

fn make_part(name: String, rust: u8) -> Part {
    Part {
        name,
        rust,
        shiny: rust == 0,
    } // field init shorthand
}

fn main() {
    let elbow = make_part(String::from("elbow"), 40);
    let knee = Part {
        name: String::from("knee"),
        ..elbow.clone()
    }; // copy the rest
    let reach = Meters(1.2);
    println!("{elbow:?}");
    println!(
        "{} has {}% rust, shiny: {}",
        knee.name, knee.rust, knee.shiny
    );
    println!("reach {} m", reach.0);
}
  • Field init shorthand: Part { name, rust, .. } when a variable has the same name as the field.
  • Update syntax: ..elbow.clone() fills in every field you didn't list.
  • Tuple structs like Meters(f64) give a plain number a meaning, so you can't pass meters where seconds were expected.
Why clone in the update syntax? Because ..elbow would move elbow's String fields into knee. Here we only take rust and shiny, which are Copy, but name isn't, so without clone the borrow checker would object if we used elbow again. Good Session 2 callback if the room is quick.

Enums

One of a fixed set of choices

#[derive(Debug, Clone, Copy, PartialEq)]
enum Direction {
    North,
    East,
    South,
    West,
}

fn opposite(d: Direction) -> Direction {
    match d {
        Direction::North => Direction::South,
        Direction::East => Direction::West,
        Direction::South => Direction::North,
        Direction::West => Direction::East,
    }
}

fn main() {
    let facing = Direction::East;
    println!("{facing:?} turns around to {:?}", opposite(facing));
}

An enum lists every possible value up front. A Direction is North, East, South or West, and nothing else. No typos, no "nort", no magic numbers.

Compare to C enums, which are just ints you can do arithmetic on, and to Python, where you'd use strings and hope. Here the compiler knows the full list, which is what makes match powerful on the next slides.

Enums with data

Each choice can carry its own luggage

#[derive(Debug)]
enum Command {
    Forward(u32),          // one number
    Turn { degrees: i32 }, // a named field
    Say(String),           // owns some text
    Charge,                // no data at all
}

fn describe(cmd: &Command) -> String {
    match cmd {
        Command::Forward(n) => format!("roll {n} squares"),
        Command::Turn { degrees } => format!("turn {degrees} degrees"),
        Command::Say(text) => format!("say '{text}'"),
        Command::Charge => String::from("plug in"),
    }
}

fn main() {
    let plan = [
        Command::Say(String::from("hi")),
        Command::Forward(3),
        Command::Turn { degrees: -90 },
        Command::Charge,
    ];
    for cmd in &plan {
        println!("{}", describe(cmd));
    }
}

This is the big one. Each variant can hold different data: a number, named fields, a String, or nothing. One type, Command, covers everything Robbie can be told to do. Today's lab is built on exactly this.

This is the feature people from other languages fall in love with. In Java or Python you'd write a class hierarchy or a dict with a "type" key. Here it's one line per variant, and match pulls the data back out safely. Mention the name for it: an algebraic data type, or "sum type".

match

Every case, or it won't compile

Fails on purpose (E0004). Press Run and read the error.

enum Light {
    Green,
    Amber,
    Red,
}

fn action(light: Light) -> &'static str {
    match light {
        Light::Green => "go",
        Light::Red => "stop",
        // forgot Amber!
    }
}

fn main() {
    println!("{}", action(Light::Amber));
}

match is exhaustive: you must handle every variant. Add the Light::Amber arm and it compiles. This is why adding a new variant later is safe: the compiler finds every match you forgot to update.

Remember this

match is a sorting machine with no floor. Every value has to land in a bin. If one could fall through, the compiler won't let you switch the machine on.

Run it, read E0004 together, then fix it live. Then ask: what if we add Light::Flashing next year? Every match on Light becomes a compile error until it's handled. Compare to a switch statement with a default that silently swallows the new case.

Patterns

match does more than names

fn mood(battery: u8) -> &'static str {
    match battery {
        0 => "asleep",
        1..=19 => "grumpy",
        20..=79 => "fine",
        80..=99 => "chipper",
        100 => "UNSTOPPABLE",
        _ => "impossible", // u8 goes up to 255, so we still need a catch-all
    }
}

fn weather(rain_mm: u32, windy: bool) -> &'static str {
    match (rain_mm, windy) {
        (0, false) => "lovely",
        (0, true) => "breezy",
        (r, _) if r > 20 => "stay inside, Robbie",
        _ => "drizzly",
    }
}

fn main() {
    for b in [0, 12, 55, 90, 100] {
        println!("{b}% -> {}", mood(b));
    }
    println!("{}", weather(35, false));
}
  • Ranges like 1..=19, and _ to catch everything else.
  • Tuples to match two things at once.
  • Bindings and guards: (r, _) if r > 20 names the value and adds a condition.
Arms are tried top to bottom, first match wins. Ask why the _ arm is needed in mood when the arms seem to cover 0 to 100 (u8 goes to 255). Swap two arms to show unreachable-pattern warnings.

if let and let else

When you only care about one shape

fn main() {
    let spare_part: Option<&str> = Some("left knee");

    // if let: only care about one pattern
    if let Some(part) = spare_part {
        println!("Fitting the {part}");
    }

    // let else: get the value or leave early
    let Some(part) = spare_part else {
        println!("No spare. Robbie limps on.");
        return;
    };
    println!("Still holding the {part}");
}

if let is a one-armed match. let ... else is its opposite: unwrap the value you need, or bail out early. It keeps the happy path flat instead of nested.

let else arrived in Rust 1.65. The else block has to leave (return, break, continue or panic), because after it the variable must exist. while let is the looping cousin; it's in the handbook.

Option

Rust has no null

fn find_part(name: &str) -> Option<u32> {
    match name {
        "elbow" => Some(12),
        "knee" => Some(7),
        _ => None, // no null: just an honest "nothing"
    }
}

fn main() {
    for name in ["elbow", "antenna"] {
        match find_part(name) {
            Some(shelf) => println!("{name} is on shelf {shelf}"),
            None => println!("no {name} in stock"),
        }
    }
}

Instead of a null that can sneak in anywhere, Rust has Option<T>: either Some(value) or None. It's just an enum from the standard library. The type tells you a value might be missing, and the compiler makes you deal with it.

Remember this

Option is a gift box. Some has a present in it, None is empty. You have to open the box before you can play with what's inside.

Tony Hoare called null his "billion-dollar mistake". Rust's answer is that a missing value is a different type. You can't call .len() on an Option<String> by accident; you have to unpack it first.

Option in practice

The box is not the present

Fails on purpose (E0308). Press Run and read the error.

fn find_part(name: &str) -> Option<u32> {
    if name == "elbow" { Some(12) } else { None }
}

fn main() {
    let shelf: u32 = find_part("elbow"); // an Option<u32> is not a u32
    println!("{shelf}");
}

An Option<u32> isn't a u32, so this is a type mismatch (E0308). Open the box with match, if let, or one of its methods:

fn find_part(name: &str) -> Option<u32> {
    if name == "elbow" { Some(12) } else { None }
}

fn main() {
    let found = find_part("elbow");
    let missing = find_part("antenna");

    println!("{}", found.unwrap_or(0)); // 12
    println!("{}", missing.unwrap_or(0)); // 0
    println!("{:?}", found.map(|s| s * 10)); // Some(120)
    println!("{}", missing.is_none()); // true

    let shelf = found.expect("the elbow should always be in stock");
    println!("shelf {shelf}");
}
Walk through unwrap_or, map and expect. Plant the flag for the next slides: unwrap() and expect() panic on None. That's fine in tests and quick scripts, and a bug waiting to happen in real code.

Result

When it can fail, say why

fn main() {
    for text in ["42", "forty-two", "-3"] {
        match text.parse::<u32>() {
            Ok(n) => println!("{text:>10} -> {n}"),
            Err(e) => println!("{text:>10} -> error: {e}"),
        }
    }
}

Result<T, E> is Ok(value) or Err(reason). Option says "maybe nothing". Result says "maybe something went wrong, and here's what".

parse is generic: the ::<u32> turbofish tells it what to parse into. Point out that "-3" fails for u32 but would work for i32. Ask the room which type they'd choose for Robbie's step count.

Your own errors

An enum of everything that can go wrong

use std::fmt;

#[derive(Debug)]
enum ChargeError {
    NoOutlet,
    Overheated { temp: u32 },
}

impl fmt::Display for ChargeError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            ChargeError::NoOutlet => write!(f, "no outlet in reach"),
            ChargeError::Overheated { temp } => write!(f, "too hot to charge ({temp} C)"),
        }
    }
}

fn charge(temp: u32, outlet: bool) -> Result<u8, ChargeError> {
    if !outlet {
        return Err(ChargeError::NoOutlet);
    }
    if temp > 60 {
        return Err(ChargeError::Overheated { temp });
    }
    Ok(100)
}

fn main() {
    println!("{:?}", charge(30, true));
    match charge(75, true) {
        Ok(level) => println!("charged to {level}"),
        Err(e) => println!("can't: {e}"),
    }
}

Your error type is just an enum. Implement Display so it prints a human sentence. Callers can match on the variant to decide what to do, or print it and move on.

This is the exact pattern the homework uses: ParseError and RobotError are enums with Display. Note Overheated carries data. Mention that crates like thiserror write the Display impl for you; we write it by hand first so it's not magic.

The ? operator

From a ladder of matches to one character

fn total_load(a: &str, b: &str) -> Result<u32, std::num::ParseIntError> {
    let x = match a.parse::<u32>() {
        Ok(n) => n,
        Err(e) => return Err(e),
    };
    let y = match b.parse::<u32>() {
        Ok(n) => n,
        Err(e) => return Err(e),
    };
    Ok(x + y)
}

fn main() {
    println!("{:?}", total_load("12", "30"));
    println!("{:?}", total_load("12", "lots"));
}
use std::num::ParseIntError;

fn total_load(a: &str, b: &str) -> Result<u32, ParseIntError> {
    let x: u32 = a.parse()?; // bad news? return it now. good news? unwrap and carry on
    let y: u32 = b.parse()?;
    Ok(x + y)
}

fn main() {
    println!("{:?}", total_load("12", "30"));
    println!("{:?}", total_load("12", "lots"));
}

? after a Result means: if it's Err, return it from this function right now; if it's Ok, unwrap it and keep going. It works on Option too.

Remember this

? is a hot potato. Good news, you keep it. Bad news, you toss it straight back to whoever called you.

Fun fact for the room: run cargo clippy on the left version and clippy literally says "this match expression can be replaced with ?". The ? also converts error types via From, which is how real projects mix error kinds; save that for Session 5.

? needs somewhere to throw

Only in functions that return Result or Option

Fails on purpose (E0277). Press Run and read the error.

fn main() {
    let n: u32 = "12".parse()?; // main returns (), so where would the error go?
    println!("{n}");
}

Fix it by having main return a Result too: fn main() -> Result<(), Box<dyn std::error::Error>>, then end with Ok(()). Or handle it right there with match.

fn first_digit(text: &str) -> Option<u32> {
    let c = text.chars().next()?; // empty text: return None right here
    c.to_digit(10)
}

fn main() {
    println!(
        "{:?} {:?} {:?}",
        first_digit("7 bolts"),
        first_digit("bolts"),
        first_digit("")
    );
}
E0277 here reads "the ? operator can only be used in a function that returns Result or Option". Show the Box<dyn Error> main and say it's a Session 5 idea we're borrowing early. The second snippet shows ? on an Option: an empty string returns None straight away.

Choosing

unwrap, expect, ? or match?

UseWhenIf it's None or Err
?Your caller should decide what to doReturns it to the caller
match / if letYou know how to handle it hereYour code runs
unwrap_or(x)There's a sensible defaultUses the default
expect("why")It truly can't happen, and you want to say whyPanics with your message
unwrap()Tests, examples, quick experimentsPanics with a generic message
Robbie says

Every unwrap() is a tiny promise that this will never fail. I made a lot of those promises about rain.

Rule of thumb for the course: library code (lib.rs) never unwraps on input it didn't create. main and tests can. Clippy has an optional lint, unwrap_used, that teams turn on in production code.

Modules

Folders for your code

mod robot {
    pub struct Robot {
        pub name: String,
        battery: u8, // private: only code inside mod robot can touch it
    }

    impl Robot {
        pub fn new(name: &str) -> Robot {
            Robot {
                name: name.to_string(),
                battery: 100,
            }
        }

        pub fn battery(&self) -> u8 {
            self.battery
        }
    }

    pub mod sensors {
        pub fn rain_detected() -> bool {
            true // it's always raining on Robbie
        }
    }
}

use robot::Robot;

fn main() {
    let r = Robot::new("Robbie");
    println!(
        "{} {}% rain={}",
        r.name,
        r.battery(),
        robot::sensors::rain_detected()
    );
}
  • mod makes a module. Everything inside is private unless marked pub.
  • use brings a name into scope so you don't type the full path every time.
  • In a real project, mod robot; in lib.rs loads src/robot.rs. The homework is split this way.
Draw the file tree for the homework: lib.rs declares pub mod parse; pub mod robot;. Inside robot.rs, use crate::parse::Command reaches across. A crate is the whole package; a module is a room inside it.

Privacy

pub on the struct isn't pub on the fields

Fails on purpose (E0616). Press Run and read the error.

mod robot {
    pub struct Robot {
        pub name: String,
        battery: u8,
    }

    impl Robot {
        pub fn new(name: &str) -> Robot {
            Robot {
                name: name.to_string(),
                battery: 100,
            }
        }
    }
}

fn main() {
    let mut r = robot::Robot::new("Robbie");
    r.battery = 255; // nice try
    println!("{}", r.name);
}

The struct is public, but battery isn't, so code outside mod robot can't touch it (E0616). That's a feature: the module decides the rules, like "battery never goes over 100", and nobody can skip them.

This is how Rust does encapsulation without classes. Getter methods like battery() give read access; a charge() method could enforce the 100 cap. Ask: what would break if anyone could set battery to 255?

Five errors you'll meet this week

Recap

What you can do now

  • Bundle data into structs and give them methods with impl.
  • Model choices with enums that carry data.
  • Handle every case with match, or one case with if let.
  • Say "maybe nothing" with Option and "maybe failed" with Result.
  • Pass errors up with ?, and split code into modules.
